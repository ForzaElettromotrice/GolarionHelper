# Equipment

Read this document when changing item definitions, inventory, containers, money, or equipped state.

- The equipment domain contains canonical definitions, concrete instances, inventory containers, equipped slots, and coin denominations. `ItemDefinition` describes a canonical item with stable ID, Italian display name, nonnegative unit weight in grams, nonnegative unit volume in milliliters (equivalent to cubic centimeters), normalized English semantic tags, an optional typed coin denomination, an optional equipment slot, declarative effects, and declarative exact-count choices. Every choice has a stable ID, Italian prompt, and named options containing ordinary item effects. It may also contain an `ItemContainerDefinition`: an identity-free template declaring the weight, volume, accepted-item, quantity-limit, outward weight/volume propagation, and possession-effect propagation behavior that each instance uses to create a concrete container. A coin definition must weigh 10 grams and cannot own a container, occupy an equipment slot, or receive effects or choices. `ItemInstance` has its own stable ID, resolves and retains a stable reference to the singleton-owned definition, and stores only its validated selected option IDs. Different instances can therefore resolve the same definition with different choices without duplicating canonical data. Instances with effects or choices have quantity one; only interchangeable inert items may be stacked.
- `ItemDefinitionManager` is a process-wide singleton with no runtime path configuration. The canonical source catalog lives at `core/resources/items.json` and CMake embeds its JSON text into the backend library, making lookup independent from the process working directory and platform asset layout. The first `get()` atomically parses and validates the complete JSON-array catalog into a `std::map`, while subsequent requests return the same stable `const ItemDefinition&`. Definitions cannot be reloaded, removed, or replaced after loading, and duplicate IDs, malformed entries, invalid effects, choices, measures, container templates, or missing definitions fail explicitly. Item behavior is parsed directly as data-driven `EffectDefinition`; there is no separate native callback registry. The catalog currently includes canonical equipped, possessed, and choice-driven examples in addition to ordinary gear and containers.
- `ItemInstance::weightGrams()` and `volumeMilliliters()` return the checked intrinsic measures of the stack as their canonical unit values multiplied by quantity; they never include contained objects. The obsolete per-item `registerWeight()`, `refreshWeight()`, and `unregisterWeight()` operations were removed because only `Inventory` has enough hierarchy context to avoid double-counting nested or extradimensional contents.
- `Inventory` owns item instances and containers in ID-indexed maps, maintains a reverse `item ID -> containing container ID` index, and always creates the unlimited virtual `worn`/`Indossati` main container. The child lists support downward aggregation while the reverse index supports ancestor traversal. `addContainer()` can register an ownerless virtual root such as `Casa` and explicitly decide whether that root contributes to carried weight; item-owned containers remain generated exclusively from their canonical item template, and the `item.` container-ID namespace is reserved for them. `CharacterSheet` owns and initializes `Inventory` in place after all expression targets and model endpoints are ready, so initial weight resolution is valid and item cleanup runs while every endpoint is still alive. There is still no general item-location type, resource-manager inventory endpoint, virtual-container removal, or general public `CharacterSheet` inventory mutation API beyond the dedicated money operations.
- A `Container` has a stable ID, Italian display name, optional owner item-instance ID, independent flags controlling whether contents weight and volume propagate beyond it, a flag controlling whether possession effects remain active beneath it, and an ordered list of direct child item IDs. A missing owner represents a virtual container such as `Indossati`; an item-backed container reuses its owner's display name while retaining a distinct ID. Possession effects are allowed only when every container from the immediate destination through the root allows them, so an inactive root such as `Casa` suppresses the complete nested subtree even through otherwise active backpacks.
- A container may independently declare optional nonnegative maximum contents weight in grams and maximum contents volume in milliliters, an accepted-item selector, and any number of nonnegative quantity limits applying to all direct contents or a selector. It owns every local rule behind two semantic operations: `validateItem()` checks direct acceptance, quantity, weight, and volume for the destination, while `validateAdditionalContents()` checks only propagated weight and volume for an ancestor. Both use one grouped `ContainerResolvers` value to recompute current direct-child measures and quantities, accept exactly up to each limit with overflow-safe subtraction, and identify the rejecting container. The individual `canAccept...()` helpers are private. Quantities count physical units rather than stack instances, filtered limits ignore nonmatching incoming items, and propagation flags never bypass the container's own internal limits.
- `ItemEffectDefinition` combines `Possessed` or `Equipped` activation with an ordinary generic `EffectDefinition`. During construction, `ItemInstance` compiles its direct effects and the effects of only its immutable selected options exactly once, using globally stable IDs derived from the item instance and definition path, and retains separate ordered `EffectApply` lists for possession and equipment. Every activation reuses those compiled functions and produces fresh cleanup callbacks for that active period. Matching effects are applied in definition order and their exact cleanups run in reverse order; a failed application cleans every earlier effect before propagating the error. `Inventory` retains possession cleanups, while its internal `Equipment` retains equipped-effect cleanups.
- `Inventory::addItem()` accepts an `ItemInstanceDefinition` plus an optional destination container ID, defaulting to `worn`. It rejects duplicate item IDs and absent destinations, delegates complete direct validation to the destination `Container`, then follows owner locations and delegates only the propagated effective-weight/effective-volume deltas to every affected ancestor before any mutation. An item whose canonical definition has container capability must have quantity one and atomically creates `item.<instanceId>` with the instance as owner and a copy of its capacity template. After structural and weight state is valid, it applies only `Possessed` effects whose complete container chain permits them and retains their cleanup callbacks by item ID. Failures roll back effects, registered weight, item, generated container, membership, and location.
- `Inventory::moveItem()` moves an existing item to a requested container or back to `worn` by default. It rejects absent references and every destination inside the moved item's own container subtree, while a move to the current container is an idempotent no-op. An equipped item must first pass through `Equipment::unequip()`, preventing inventory mutations from leaving stale slot assignments. Destination and ancestor limits are checked against the complete effective weight and volume of the moved subtree after excluding that same subtree from its old branch, preventing double-counting across shared ancestors. A successful move updates membership, reverse location, aggregate carried weight, and `Possessed` effects for every affected descendant in parent-first/reverse order according to its new complete container chain. Validation, allocation, weight-update, or effect-application failure restores the old hierarchy, weight, and effect state atomically.
- `Inventory::removeItem()` rejects absent items, equipped items, and nonempty container items. For a valid removal it resolves the item's exact contribution through every weight-propagating ancestor, updates the aggregate encumbrance entry, runs retained possession cleanup in reverse order, removes the direct membership and reverse location, destroys an empty generated container, and finally erases the instance. The inventory destructor also cleans every still-active item effect. Removing anything below an ancestor that ignores contents weight leaves the registered total unchanged. Recursive deletion is deliberately unsupported so removing a container can never silently destroy its contents.
- `Inventory` is the sole inventory-weight source for `Encumbrance`: its constructor registers the single `inventory.totalWeight`/`Inventario` entry, and successful mutations replace it with the checked recursive sum of effective items rooted under every virtual container whose `contributesToCarriedWeight` flag is true. A newly constructed `CharacterSheet` therefore exposes this zero-valued source in `EncumbranceView`. Virtual roots such as `Casa` may remain outside carried weight, while an abstract carried borsello may opt in. Ordinary carried containers add their entire subtree; `ignoresContentsWeight` stops propagation after its own intrinsic weight. Volume follows the equivalent recursion for ancestor capacity checks, with `ignoresContentsVolume` stopping outward volume. The recursive resolvers and move validation detect corrupt or newly requested cycles defensively. GUI failure details and virtual-container removal remain pending.
- `InventoryView` exposes total carried weight, every item with canonical identity/name/tags, quantity, intrinsic and subtree-effective measures, location, generated container, equipment slot, equipped state, possession-effect activation, and every definition choice with the selected options marked for the GUI; every container exposes its rules, direct members, current effective contents measures, and carried-weight role; all fourteen equipment slots are always present with capacity and assignments. Its derived `MoneyView` includes only containers that directly contain coins, reports the four denomination quantities plus intrinsic coin weight for each one, keeps nested containers separate, and exposes the corresponding global denomination/weight sum without storing duplicate state. Save format 23 stores user-owned virtual containers plus item identity, definition, quantity, selected choice IDs, location, and equipped state. Coins therefore persist as ordinary items and require no separate money save data. The fixed `worn` container and item-owned containers are rebuilt, not serialized. Loading creates virtual roots first, resolves item-owned-container dependencies topologically, rejects missing/cyclic locations, validates choices against the current canonical definition, and equips saved items only after every instance exists; older inventory JSON without `choices` is read as an empty selection list.
- `Inventory` owns a stateless `Money` facade. `Money::add()` creates or increases the canonical denomination stack directly inside the requested container; `Money::remove()` consumes matching direct stacks deterministically and rejects an insufficient amount before mutation. Both paths reuse inventory validation and atomically maintain container/ancestor limits and aggregate carried weight. Generic item insertion, movement, and removal remain valid for coins, and the derived View recognizes those changes. `CharacterSheet::addMoney()` and `removeMoney()` are the GUI-facing convenience operations and always require an explicit container ID.
- `Inventory` directly owns one internal `Equipment` and is the sole public coordinator through `Inventory::equip()` and `Inventory::unequip()`. `Equipment` has no public mutation API and owns only the assignments for all fourteen Pathfinder magic-item slots plus their `Equipped` effect cleanups: Anello, Armatura, Cintura, Collo, Corpo, Fronte, Mani, Occhi, Piedi, Polsi, Scudo, Spalle, Testa, and Torace. Anello accepts two physical items; every other slot accepts one. Slots are not inventory containers. On equip, `Equipment` validates the definition, quantity, and slot capacity; `Inventory` transactionally moves the instance from its previous container into `worn`/`Indossati`; then `Equipment` records the assignment and applies the equipped effects. A failure in either layer rolls the movement, assignment, weight, possession effects, and equipped effects back together. On unequip, `Equipment` removes its assignment and effects, while `Inventory` leaves the item in `Indossati` by default or moves it to an explicit container. Ordinary inventory movement and removal reject equipped instances so slot state cannot become stale. Hand usage and wielding are deliberately outside this step.
