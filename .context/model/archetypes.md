# Class Archetypes

Read this document when changing archetype definitions, compatibility, class feature replacement or archetype persistence. Base class progression is described in [classes.md](classes.md).

## Definition and Catalog

- `ArchetypeDefinition` identifies an owning `CharacterClassType`, ID and Italian name/description. `affectedFeatures` names original class feature IDs with closed Alter/Replace semantics. Structural edits are separate: removed whole feature IDs, removed acquisition IDs and added `ClassFeatureDefinition` values with ordinary progression/effects/nested choices. This schema does not change class base tables, hit dice or skill metadata.
- `ClassDefinitionManager` accepts an optional immutable archetype catalog and exposes `getArchetype(id)`. Catalog insertion rejects duplicate IDs and missing owning classes. Catalogs are still supplied as typed definitions; default content is empty and JSON definition loading is deferred.

## Runtime

- `Classes::addArchetype(type, id)` requires the character to already possess that class. `CharacterSheet::addClassArchetype` forwards and rechecks feat prerequisites. CharacterClass owns snapshots of selected archetype definitions, indexed together with the original features.
- Compatibility compares original affected feature IDs across every selected archetype, including future levels, regardless of whether the action is Alter or Replace. This follows the [Golarion class-archetype rule](https://golarion.altervista.org/wiki/Classi). Different removed acquisition IDs do not make two edits of the same original feature compatible.
- Validation rejects wrong-class or duplicate selections, missing/duplicate original impacts, undeclared removals, invalid impact enums, replacements that omit whole-feature removal, and colliding feature/acquisition/effect IDs. Added progression `replaces` references must stay within the same archetype's new acquisitions; original removals must use structural edits, preventing undeclared replacement of another feature. Ordinary progression and dependency-cycle validation also runs before activation.
- Structural removals disable original acquisitions before checking level thresholds, including their nested branches. Unaffected acquisitions and their registrations remain intact. New benefits unlock at their own levels. Original choices remain stored and visible as inactive rather than being deleted.
- Added features use the existing `selectOption` / `unselectOption` pathway at CharacterClass/Classes and `selectClassOption` / `unselectClassOption` on the sheet. No separate archetype choice engine is needed.
- Adding an archetype snapshots indexes and compiled callbacks, stages new additions before removing obsolete effects, and restores indexes/selection metadata if validation or application fails. Unchanged feat selections and limited-use counters are preserved. As with the base runtime, conflicting exclusive endpoints reject a transition rather than destructively rebuilding old state; cleanup callbacks must not throw.
- `Classes::removeArchetype(type, id)` and `CharacterSheet::removeClassArchetype` remove a selected archetype; the sheet rechecks feat prerequisites afterward. Removal deletes all its added acquisitions/effects and their choices, restores original acquisitions at the current level, and resets choices throughout the original features declared in its `affectedFeatures` (including nested/inactive branches). Other archetypes and unrelated feature choices/registrations remain intact. Re-adding the removed archetype starts with no old choices.
- Removal stages index/callback changes and restores original effects before withdrawing obsolete ones. If restoration fails, it rolls back indexes and leaves archetype selection, choices and existing effects intact. The same exclusive-endpoint limitation and nonthrowing cleanup requirement as addition apply. The player decides when removal/retraining is allowed; no timing rules are enforced.

## Data, View and Verification

- Format 31 saves selected archetype IDs per class, plus existing class levels and choice IDs; definitions/effects are not serialized. Format 30 loads with no archetypes. The sheet still accepts the previous supported formats.
- Classes restores selected archetypes at level zero before loading level/choices, then the sheet restores dependent feat and spell state. Duplicate, missing or incompatible saved archetypes are rejected. Direct CharacterClass::load requires the saved archetype set to match the already installed definitions.
- CharacterClassView includes selected archetype ID/name/description and the new feature snapshots; original removed acquisitions remain visible with active=false and preserved choices.
- Tests cover multiple compatible archetypes, whole/partial and nested-branch removal, future-level conflicts, new choices via existing APIs, progression, rollback with selected feats/consumed spells intact, invalid edits/collisions, JSON round trips and format-30 compatibility. Removal tests additionally cover original choice reset, unrelated choice/feat/use preservation, another archetype remaining selected, re-addition without old choices, round trips after removal and failed-restoration rollback/retry. Format 31 already represents the resulting state; no format bump is needed. No play module tests are involved.
