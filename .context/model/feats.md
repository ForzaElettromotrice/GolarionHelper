# Per-character Feats

Read when changing feat slots, acquisition, qualification, or effect ownership.

## Declarative slot grants

`FeatSlotGrantEffectDefinition` is parsed as `featSlotGrant`. Its optional `filter` is `{ "kind": "any" }` (also the default), `{ "kind": "type", "featType": "combat" }`, or `{ "kind": "ids", "featIds": ["improvedInitiative"] }`. Empty ID lists, duplicate normalized IDs, blank types/IDs, and ambiguous filters are rejected. Compilation registers `FeatSlot` with the owning effect's stable instance ID/source and returns cleanup that withdraws that exact slot, including the selected feat's effects. The filter types live in `feat_slot_filter.hpp` to avoid coupling effect definitions to the runtime.

This enables race/item/class-owned slots; no shipped catalog has been migrated yet. Slots granted by acquired feats themselves are explicitly rejected before application: the current recheck rebuilds feat effects and would otherwise erase nested selections or reenter the solver. Nested-slot lifecycles and declarative prerequisite-alternative/exemption behavior remain separate work.

- `CharacterSheet` owns `Feats`, which owns `FeatPrerequisiteRegistry` and registers the typed `feat.slots` collection. Source-owned slots carry a stable ID, source, and one explicit filter: any feat, one `FeatType` enum value, or a nonempty list of canonical IDs. An optional source callback exempts individual requirements; an exemption never overrides slot eligibility.
- `Feats::setLevel()` maintains one ordinary slot for each odd level, with stable IDs `base.feat.level1`, `base.feat.level3`, etc. This prefix is reserved. Lowering the level withdraws the affected slots and their active effects. The current sheet still has fixed level 1, so it initializes only the first ordinary slot. Future character-level progression must call this method.
- `selectFeat(slotId, featId, choices)` requires an empty slot and a complete valid set of internal choices. Definitions come from `FeatDefinitionManager`; types and allowed IDs are checked before requirements. Each nonexempt automatic requirement is evaluated through `ExpressionParser` using the registry's candidate values. Repeated references to one target use one consistent value per evaluation. Multiple targets are searched across candidate combinations; distinct requirements must all pass. Source callbacks remain responsible for contextual applicability.
- Requirements with neither an expression nor a structured feat dependency are informational and do not block acquisition or use, by explicit user decision. Unknown targets and expression errors still propagate. The registry does not contain exemption rules.
- Direct effects and selected option effects are compiled before application, applied in definition order, and cleaned in reverse order. If application fails, earlier applied effects are rolled back and the slot stays empty. `removeFeat()` clears effects and selection while preserving the slot. A source withdrawing a slot through the resource collection also clears its feat.
- `FeatDefinition::repeatability` is `Once` by default, `DifferentChoices` for different complete choice sets, or `Unlimited`. JSON uses `once`, `differentChoices`, and `unlimited`. Option IDs are sorted before storage/comparison; changing their order does not create a new selection. Inactive acquisitions still count for uniqueness. Effects have slot-specific IDs and retain their declared stacking semantics. To change an occupied slot, remove its feat first.
- A requirement may contain `feat: {id, matchingChoices}` instead of `expression`. It requires another active acquisition of that definition. Optional `matchingChoices` maps prerequisite choice IDs to the current feat's choice IDs, allowing requirements such as the same weapon. This works on direct and selected-option requirements and remains subject to source exemptions. The current slot cannot satisfy its own dependency.
- `Feats::recheckPrerequisites()` removes feat effects, then evaluates simultaneous activation states until stable. This propagates chains independently of slot order and prevents cycles from sustaining themselves without an external qualifying starting point. Repeated activation states indicate nonconvergence and raise an error. Evaluation/application errors remove all feat effects but preserve acquisitions for correction/retry; unrelated sheet mutations are not rolled back.
- Rechecks occur on selection/removal, level changes, source slot withdrawal, and after loading all selections. `CharacterSheet` invokes them after relevant ability, skill, race, condition, hit-point, identity-rule, and money mutations and before producing its View. `recheckFeatPrerequisites()` remains available explicitly. Standalone `Feats` users must call `recheckPrerequisites()` after changing external targets or prerequisite-alternative callbacks; no generic resource observer was added. Future sheet mutation APIs must follow the same recheck convention.
- `CharacterSheet` forwards select/remove operations. `FeatsView` separates acquired `FeatView` entries (slot ID, definition ID, name, description, types, selected choices with prompts/option names, and the derived `active` flag) from slots (ID, source, selected feat ID, and type/ID restrictions). Slot IDs distinguish repeated acquisitions. Empty slots remain visible. No catalog browsing interface or frontend was added.
- `FeatsData` stores only selected slot IDs, feat IDs, and choice/option IDs. Sheet format 25 includes this data; older JSON formats load with no feat selections. Effects are reconstructed from the catalog, never serialized. `Feats::load()` requires empty slots and validates slot eligibility and choice structure, then restores each acquired feat as active or inactive according to current prerequisites, rolling back all selections from that load on failure. Inactive acquisitions are saved with the same IDs/choices; the active flag is derived, never persisted. Unknown slots/feats, duplicates, and invalid choices are errors.
- The sheet restores feats after race, skills, conditions, and inventory. Source-owned slots and prerequisite callbacks must be reconstructed by their owners before feat loading. They are not serialized. All selections are restored before the shared activation solver runs, so load order does not determine dependency activation. Unsupported cycles remain acquired but inactive.

Rules references: [Talenti](https://golarion.altervista.org/wiki/Talenti), [Arma Focalizzata](https://golarion.altervista.org/wiki/Arma_Focalizzata) for distinct-choice repetitions, and [Ira Extra](https://golarion.altervista.org/wiki/Ira_Extra) for cumulative repetitions. These examples were not added to the shipped catalog.
