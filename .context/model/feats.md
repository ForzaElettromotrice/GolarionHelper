# Per-character Feats

Read when changing feat slots, acquisition, qualification, or effect ownership.

## Custom definitions and user-owned extra slots

- `CharacterSheet::addCustomFeatDefinition(FeatDefinition)` registers an immutable definition in its `FeatCatalog`. Lookup checks local definitions before the standard-only `FeatDefinitionManager`; IDs cannot collide with either catalog. Validation/normalization uses the same bidirectional JSON codec, preserving enum types, requirements, dependency choice bindings, repeatability, effects and choices. No update/removal API is introduced.
- The sheet injects its catalog into `Feats` and owns it longer than the runtime selections. Standalone `Feats` optionally accepts a non-owning catalog pointer, otherwise using the standard manager. Registration does not select a feat or apply effects; custom feats work in ordinary and extra slots.
- `addExtraFeatSlot(slotId)` creates a user-owned, unrestricted slot; `selectFeat` fills it. `removeFeat` clears its selection but retains the slot; `removeExtraFeatSlot` removes the slot and any selected effects. Base-level IDs are reserved, duplicate IDs (including unavailable source records) reject, and provider endpoints cannot revoke user-owned extra slots.
- Extra slots ignore all direct and selected-option prerequisites, including structured feat dependencies and unresolved expressions, both on selection and on every subsequent recheck. Choice structure and repeatability still apply. Their effects use the ordinary compiler, stacking, ownership and reverse cleanup; they remain active across level changes and can satisfy other feats' dependencies normally. No simulation or special effect application path is added.
- `FeatSlotOrigin` is a closed enum (`Source`, `Extra`) exposed by slot Views. `FeatsData.extraSlotIds` persists user-owned slots, including empty ones; source-owned slots still come only from their providers. Saved selections remain slot/feat/choice IDs. Loading reconstructs extra slots before selection and rolls back newly created slots/selections on failure.
- Sheet format 39 persists `customFeatDefinitions` and extra slot IDs. Definitions load before source reconstruction; Data and View expose complete custom definitions. Older supported formats have no custom feats/extra slots. `custom_feats_test` covers isolated catalogs, codec validation, standard/custom acquisition, prerequisite bypass, normal dependencies, cleanup, level independence, ownership, save/load and legacy format 38.

## Current Lifecycle

User selections survive source-slot withdrawal, level decreases and save/load without their provider. Slot availability remains separate from feat activation; unavailable slots do not retain provider callbacks.

Prerequisites are checked against live active feats, by user decision. No numerical projection or temporary sheet state is used. The previous simulation experiment remains removed; see [the rollback decision](../history/2026-11-10-feat-evaluation.md).

Valid active feats retain their effects and mutable state across checks. Feat-owned slots and favored-class slot rewards are supported, including source loss, reacquisition, save/load and cleanup. Genuine deactivation still removes owned effects; reactivation creates them again. The embedded catalog remains unchanged.

## Declarative slot grants

`FeatSlotGrantEffectDefinition` is parsed as `featSlotGrant`. Its optional `filter` is `{ "kind": "any" }` (also the default), `{ "kind": "type", "featType": "combat" }`, or `{ "kind": "ids", "featIds": ["improvedInitiative"] }`. Empty ID lists, duplicate normalized IDs, blank types/IDs, and ambiguous filters are rejected. Compilation registers `FeatSlot` with the owning effect's stable instance ID/source and returns cleanup that withdraws that exact slot, including the selected feat's effects. The filter types live in `feat_slot_filter.hpp` to avoid coupling effect definitions to the runtime.

This enables race/item/class/feat-owned slots and favored-class slot rewards. Selected feats survive source withdrawal as unavailable acquisitions. Nested cleanup does not start a recursive prerequisite check, and the next pass reads fresh slot IDs.

- `CharacterSheet` owns `Feats`, which owns `FeatPrerequisiteRegistry` and registers the typed `feat.slots` collection. Source-owned slots carry a stable ID, source, and one explicit filter: any feat, one `FeatType` enum value, or a nonempty list of canonical IDs. An optional source callback exempts individual requirements; an exemption never overrides slot eligibility.
- `Feats::setLevel()` maintains one ordinary slot for each odd level, with stable IDs `base.feat.level1`, `base.feat.level3`, etc. This prefix is reserved. Lowering the level marks occupied slots unavailable and removes their effects without discarding selections; empty withdrawn slots are removed. Raising the level restores the same slot IDs and rechecks retained talents. The sheet now derives total level from Classes (initially zero) and updates these slots on class advancement. Format-30 loading reconstructs class-owned slots before feat selections; legacy saves retain an acquired first-level feat through the explicit migration flag described in [classes.md](classes.md).
- `selectFeat(slotId, featId, choices)` requires an empty slot and a complete valid set of internal choices. Definitions come from the injected `FeatCatalog`, falling back to `FeatDefinitionManager`; types and allowed IDs are checked before requirements. Each nonexempt automatic requirement is evaluated through `ExpressionParser` using the registry's candidate values. Repeated references to one target use one consistent value per evaluation. Multiple targets are searched across candidate combinations; distinct requirements must all pass. Source callbacks remain responsible for contextual applicability.
- Requirements with neither an expression nor a structured feat dependency are informational and do not block acquisition or use, by explicit user decision. Unknown targets and expression errors still propagate. The registry does not contain exemption rules.
- Direct effects and selected option effects are compiled before application, applied in definition order, and cleaned in reverse order. If application fails, earlier applied effects are rolled back and the slot stays empty. `removeFeat()` explicitly clears effects and selection, keeping an available slot but deleting an unavailable record. Withdrawing a source marks occupied slots unavailable and deactivates their feats without deleting selections; empty slots are removed. Provider exemption callbacks are immediately released so unavailable records cannot reference destroyed sources.
- `FeatDefinition::repeatability` is `Once` by default, `DifferentChoices` for different complete choice sets, or `Unlimited`. JSON uses `once`, `differentChoices`, and `unlimited`. Option IDs are sorted before storage/comparison; changing their order does not create a new selection. Inactive acquisitions, including those in unavailable slots, still count for uniqueness; the player must explicitly remove an old selection to acquire a conflicting replacement. Effects have slot-specific IDs and retain their declared stacking semantics. To change an occupied slot, remove its feat first.
- A requirement may contain `feat: {id, matchingChoices}` instead of `expression`. It requires another active acquisition of that definition. Optional `matchingChoices` maps prerequisite choice IDs to the current feat's choice IDs, allowing requirements such as the same weapon. This works on direct and selected-option requirements and remains subject to source exemptions. The current slot cannot satisfy its own dependency.
- `Feats::recheckPrerequisites()` checks active feats without first removing benefits. Deactivation passes repeat until no active feat fails; then one qualifying inactive acquisition is activated and evaluation restarts with fresh slot IDs. This propagates dependency losses and restoration without reapplying unchanged effects. Reentrant checks during a pass or effect application/cleanup are handled by the outer operation; prerequisite callbacks must remain read-only. Cleanup detaches its callbacks and marks the feat inactive before invoking them. Destruction suppresses reactivation and uses stable ID lookups. Repeated states (IDs, availability, activation) raise a nonconvergence error rather than looping; existing active circular support is not proactively dismantled. Errors preserve acquisitions and unchanged effects; failed activation rolls back its own additions, but prior successful transitions and unrelated sheet changes are not rolled back.
- Rechecks occur on selection/removal, level changes, source slot withdrawal, and after loading all selections. `CharacterSheet` invokes them after relevant ability, skill, race, condition, hit-point, identity-rule, inventory, casting, and money mutations and before producing its View. `recheckFeatPrerequisites()` remains available explicitly. Standalone `Feats` users must call `recheckPrerequisites()` after restoring a slot source, changing external targets or prerequisite-alternative callbacks; no generic resource observer was added. Future sheet mutation APIs must follow the same recheck convention.
- `CharacterSheet` forwards select/remove operations. `FeatsView` separates acquired `FeatView` entries (slot ID, definition ID, name, description, types, selected choices with prompts/option names, and the derived `active` flag) from slots (ID, source, selected feat ID, and type/ID restrictions). Slot IDs distinguish repeated acquisitions. Empty slots remain visible. No catalog browsing interface or frontend was added.
- `FeatsData` stores selected slot IDs, feat IDs and choice/option IDs plus user-owned extra slot IDs since format 39; availability and activity remain derived, never persisted. `Feats::load()` requires no prior selections, validates feat identity, choice structure and repeatability, and rolls back both acquired selections and newly created unavailable records on failure. Missing source slots are restored as unavailable placeholders with an Italian generic source label; they grant no permissions, exemptions or effects. Known slots with changed incompatible filters retain the saved feat as inactive. Unknown feat IDs, duplicate acquisitions and invalid choices remain errors; an unknown slot ID is intentionally preserved for a possibly absent source, not treated as an available grant.
- The sheet restores feats after race, skills, conditions, and inventory. Source-owned slots and prerequisite callbacks must be reconstructed by their owners before feat loading. They are not serialized. All selections are restored before the shared activation solver runs, so load order does not determine dependency activation. Cycles with no initially active qualifying member remain inactive on load; no special cycle-breaking simulation is performed.

Rules references: [Talenti](https://golarion.altervista.org/wiki/Talenti), [Arma Focalizzata](https://golarion.altervista.org/wiki/Arma_Focalizzata) for distinct-choice repetitions, and [Ira Extra](https://golarion.altervista.org/wiki/Ira_Extra) for cumulative repetitions. These examples were not added to the shipped catalog.
