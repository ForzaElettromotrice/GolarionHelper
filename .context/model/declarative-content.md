# Declarative Content

Read this document when changing shared declarative effects or feat definitions.

- `EffectDefinition` is a reusable, type-safe `std::variant` shared by races, items, and future class, feat, or other declarative sources. Its initial alternatives describe modifiers, accumulated contributions, the race-owned size base, movement grants, the race-owned carrying body type, and GUI reminders. Every effect has a source-local stable ID. The stateless `compileEffect` function receives one definition plus an `EffectContext` containing the globally stable instance ID and GUI source derived by its owner; it returns an apply callback whose only argument is `ResourceManager`, and applying it returns the exact cleanup callback. All six current alternatives are translated through their existing resource entry points. `effectDefinitionFromJson()` parses the same alternatives from stable English JSON type names, while non-automatable rule text is represented as a reminder rather than an opaque native callback. Further typed collection alternatives, definition managers, and source-owned cleanup lifecycles remain separate later steps.
- `FeatDefinition` is the declarative, frontend-independent description of a feat. It carries a stable ID, Italian name and complete rules text, open semantic type IDs, requirements, unconditional typed effects, and optional exact-count choices. Each requirement contains Italian display text plus an optional machine-checkable expression or structured feat dependency. Text-only requirements are informational and ignored by explicit user decision. Choice options may own their own requirements and effects, allowing selections such as a weapon to validate and modify a different semantic resource. Repeatability is explicit (`once`, `differentChoices`, or `unlimited`); separate Normal/Special fields remain in the complete description. `featDefinitionFromJson()` now parses these fields, preserves text-only requirements for display, validates array shapes and required text, rejects duplicate normalized type/choice/option/effect IDs within their owning scope, and enforces positive integral selection counts bounded by the available options. It validates expression storage, not runtime resource availability or prerequisite satisfaction. The per-character runtime, selection persistence, and Views are documented in [feats.md](feats.md).

- `FeatDefinitionManager` follows the race-definition singleton: the first `get()` parses the complete embedded `core/resources/feats.json` catalog into a temporary map, rejects duplicate feat IDs, and publishes it only after successful validation. Lookups normalize IDs, return stable immutable references, and reject missing definitions. CMake embeds the catalog and regenerates it when its JSON changes; no runtime filesystem path is needed. The initial entry is Iniziativa Migliorata (`improvedInitiative`), a generic +4 initiative modifier. Rules reference: [Golarion](https://golarion.altervista.org/wiki/Iniziativa_Migliorata), with its linked English name Improved Initiative. Catalog loading does not apply effects or evaluate prerequisites.
