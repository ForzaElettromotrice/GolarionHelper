# Spells

Read when changing spell definitions or designing spell catalog/loading and casting sources.

For the metamagic structures and separate preparation/casting grant endpoints, read [metamagic.md](metamagic.md). They are owned by `Spellcasting` and consulted by `prepare()`/`consume()`, including atomic source-use payment.

## Current definition

- The C++ definition is ported from the existing Java `SpellDefinition`, `SpellData`, `SpellSavingThrowData`, and associated enums on `master` at `8f81a09` (also verified against `origin/master`). Do not replace that established schema with open category strings.
- `spell_types.hpp` contains the closed spell vocabularies recovered from that branch. The shared class enum now lives in `character_class_type.hpp`, included by `spell_types.hpp`, and adds `Adept` without changing existing enumerator values.
- `SpellDefinition` is a value aggregate with an added stable catalog ID. It retains the previous separate typed maps `spellLevelByClass`, `spellLevelByDomain`, and `spellLevelByBloodline`. The former Java `DomainSpellListType` interface becomes a `std::variant<DomainType, SubdomainType>`. Levels are spell levels, not caster levels or acquisition levels.
- Descriptor/component sets use `std::set<enum>`, replacing Java EnumSet. Subschool, material/focus details, material cost, target, effect, and area are optional. Casting time, range, duration, and resistance have both an enum category and Italian explanatory text. Saving throws are a vector of typed save/effect/description records, reusing the existing `SavingThrowType`; an empty vector represents no save.
- `validateSpellDefinition()` checks required text, enum values, school/subschool compatibility, nonnegative levels/costs, nonempty and consistent components, material/focus prerequisites, concentration/dismissible consistency from the legacy model, and save entries. Unlike the immutable Java builder, the C++ aggregate is mutable and validation is explicit; callers must validate after editing. The JSON loader validates every definition on entry. The validator does not normalize fields in place.
- This port preserves the existing enum vocabulary rather than claiming an exhaustive catalog audit. Any additional category must be added explicitly to its enum and validation, never admitted as an arbitrary string.
- No Java builder, search filters, GUI labels, or subdomain-to-parent-domain lookup machinery was imported. The sheet owns the casting container and persists its mutable state in format 27; sheet casting operations and cast-effect runtime remain pending. Metamagic validation/payment and preparation state are implemented; see the linked topic. Slot grants, prepared-slot transitions, and Data/View are implemented below. Do not infer mechanics from descriptions.

## Catalog and manager

- `SpellDefinition::effects` is an initially empty `std::vector<EffectDefinition>`, parsed with the existing shared effect JSON parser. Missing/null/empty `effects` means no mechanical effects; non-array values, unknown effect types, malformed entries and duplicate/blank normalized IDs reject. Native validation also checks effect IDs. The existing singular `effect` remains descriptive text, independent of the new plural list. This is definition-only metadata: nothing is compiled, targeted, applied or removed automatically by casting, and the production spell catalog is unchanged.

- `SpellDefinitionManager::instance().get(id)` lazily loads the embedded `resources/spells.json` catalog and returns a stable const reference. Loading is mutex-protected; the complete catalog is validated in a temporary map before publication. Duplicate normalized IDs and unknown lookup IDs are rejected.
- `spellDefinitionFromJson()` follows the legacy Java field names and `UPPER_SNAKE_CASE` enum names, converting them strictly into enum values. Unknown enum names, duplicate normalized set/list entries, malformed collection types, and non-integer/out-of-range levels or costs are rejected. Text is trimmed; absent/null optional collections are empty, absent/null/blank optional descriptions are unset, and absent/null `dismissible` is false. Required model invariants are then validated.
- Unlike the legacy JSONL repository, the embedded catalog is a JSON array and each definition has a stable `id`. Class and bloodline level maps retain flat enum-name keys. Domain levels explicitly distinguish the two enum namespaces: `"spellLevelByDomain": {"domain": {"HEALING": 1}, "subdomain": {"HEALING": 2}}`. This avoids the old parser's domain-first ambiguity when a domain and subdomain share a name.
- The runtime JSONL catalog on `master` at `8f81a09` is effectively empty. Its separate scraped `scripts/spells.json` data has not been imported. The current C++ catalog contains only `fireball` (Palla di Fuoco), with a short descriptive summary; bulk catalog expansion remains deferred.
- Focused tests cover manager lookup/reference stability, complete and minimal JSON records, optional values, domain/subdomain disambiguation, enum conversion, malformed input, and validation failures.

## Spellcasting skeleton

- `Spellcasting` is an abstract base with a protected constructor requiring `ResourceManager&`, a stable casting ID, and `CharacterClassType spellListClass`, and a public pure virtual destructor defined in the implementation. It validates that the selected class identifies a supported list and owns its slot collection endpoint. The manager must outlive the instance. Copy and move are disabled because callbacks capture the instance address.
- `PreparedSpellcasting`, `SpontaneousSpellcasting`, and `FlexibleSpellcasting` forward those constructor arguments to the base. The former `SpellcastingMode` enum and stored mode were removed: the concrete type identifies the behavior. All three variants implement consumption. Tests cover all lists, invalid enum values, and ownership through `std::unique_ptr<Spellcasting>`.
- The separate `SpellList` enum/header was removed in favor of `CharacterClassType`, matching the keys already used by spell definitions. The constructor parameter identifies the list to consult, not the owner granting casting; e.g. a racial ability may select `Wizard`. Shared lists now use the exact selected class key, without fallback to sibling classes. Non-list classes such as Fighter are rejected by the casting constructor, although valid in the general class enum.
- The [Golarion catalog index](https://golarion.altervista.org/wiki/Database_Incantesimi) informed the supported lists, including Adept and the separate unchained summoner list. Alchemist/Investigator select formula metadata only; extract mechanics remain unimplemented. Domains, subdomains, and bloodlines remain separate supplemental metadata.
- `SpellDefinition::spellLevelByClass` and its JSON shape are unchanged, with `ADEPT` added to strict enum parsing and definition validation. Selecting a class does not grant or load all its spells.
- The base stores `repertoire_` as an initially empty `std::set<std::string>` of spell definition IDs, independently for each instance. `addToRepertoire(id)` trims and inserts an ID idempotently, rejecting blank IDs. It does not resolve the catalog or automatically populate the selected list; effective availability is checked during preparation.
- `Spellcastings` now owns independent casting instances in the sheet (see below); a separately granted spell is not forced into a full spellcasting instance. The repertoire will be populated externally (including full-list access). Book/familiar dependencies are deferred.

## Casting container and source ownership

- `CharacterSheet` owns an initially empty `Spellcastings`, constructed before feats/race/inventory and destroyed after them. Its ResourceManager outlives it. The container is non-copyable/non-movable and registers the typed collection endpoint `spellcastings` (`Spellcastings::Resource`).
- `SpellcastingGrant` contains a source-chosen stable `id`, descriptive `source`, closed `SpellcastingMode` (Prepared/Spontaneous/Flexible), and `CharacterClassType spellListClass`. The mode selects the concrete class at creation; the instance itself still uses its concrete type, not a stored mode flag. IDs/source are trimmed and must be nonblank; duplicate normalized IDs, invalid modes and non-list classes are rejected.
- Adding a grant constructs the concrete casting and its endpoints; removing the grant destroys it and its state and unregisters its endpoints. Failed construction rolls back only its own registrations. Re-adding starts empty. Owners must remove dependent contributions before removing the casting; no cross-source dependency scheduler is introduced.
- `get(id)` returns a mutable base reference for repertoire and concrete casting operations, valid until removal or container destruction. It does not transfer ownership. The current sheet facade does not expose casting operations or its ResourceManager; future internal providers receive the existing registry by reference.
- Sources already know their chosen ID (e.g. `class.wizard`) and address instance endpoints with helpers such as `spellSlotsResource(id)`. Multiple instances may select the same class list without sharing state. No slots, repertoire, metamagic or class features are inferred from creation.
- Level progression belongs to the granting source: keep the casting instance and replace its slot grants when progression changes. This resets the affected group as agreed, but preserves the repertoire and other groups/instances. Class level, spell progression and caster level are distinct concepts; no generic `setLevel()` or automatic progression is added.
- Container save data, sheet JSON and aggregate View are implemented. `Spellcastings::toView()` returns entries ordered by stable casting ID, each with source, closed mode enum, sorted repertoire IDs and a closed variant containing the existing Prepared/Spontaneous/Flexible View. The mode enum lives in `spellcasting_mode.hpp`, shared by grants and Views. Snapshots own their data and remain valid after slot changes or grant removal; no runtime callback or mutable handle is exposed. `CharacterSheetView.spellcastings` includes the snapshot, empty when no casting is granted. Sheet operations, declarative effect parsing, custom resolver configuration through the creation grant and concrete class providers remain separate steps. Focused tests cover all modes, isolation, stable identity during slot replacement, validation, removal/recreation, endpoint collision rollback, destructor cleanup and detached aggregate Views.

## Container persistence (format 27)

- `SpellcastingsData` holds entries with stable casting ID, repertoire IDs and a closed variant of Prepared/Spontaneous/Flexible state data. JSON uses stable English mode/metamagic names and typed option objects. Prepared linkage, consumed flags, flexible selections and consumed casting slots round-trip independently.
- Save data does not grant casting capabilities or serialize slot capacities, filters, callbacks, metamagic permissions or source pool balances. Sources must reconstruct all instances and grants before `load()`. The saved ID set must exactly match the granted set, and each state variant must match its concrete casting. Unknown/missing/duplicate IDs fail rather than silently dropping state. Source-owned pools retain their balances and need source persistence separately.
- The container stages all instance states and repertoires, validating against restored repertoire choices and current grants, before committing non-throwing swaps. An error in a later entry leaves every live instance unchanged. Existing object identities remain stable. Loading never pays, refills or refunds usage pools. Provider callbacks must remain pure as for ordinary preparation.
- `CharacterSheet` saves format 27 and restores casting state after race, inventory, feats and prerequisite reconciliation. Supported pre-27 formats retain their earlier migrations and no saved casting state. Concrete casting providers are not yet implemented: a nonempty casting save cannot invent a class/item/racial grant during sheet loading; standalone container tests explicitly reconstruct sources.
- JSON rejects unknown modes/metamagic/energy names, wrong arrays/options, fractional/negative/overflowing slot values and invalid metamagic option ranges. Domain loading additionally validates normalized IDs, grants, repertoire, slots and spell applicability.
- Tests cover all three modes, linked consumed preparations, exhausted source pools, deterministic JSON round trips, all choice-bearing metamagics, atomic cross-instance rejection, malformed JSON and pre-27 compatibility. All 68 sheet tests pass; no play tests are included.

## Slot grants

- Each instance registers `spellcasting.<castingId>.slots`, named through `spellSlotsResource(castingId)`, as a typed `SpellSlotGrant` collection. Its destructor unregisters the endpoint. Different casting instances keep independent groups, including when grant IDs match.
- A grant contains a source-owned stable `id`, descriptive `source`, a nonempty `dailyCapacityByLevel` map (levels 0–9, positive capacities), and optional `allowedSpellIds` shared by all levels. For example, `{{1, 3}, {2, 2}}` grants three first-level slots and two second-level slots in one entry. Zero capacity is represented by omitting that level; this does not model whether a spell level is unlocked. Validation of all levels completes before insertion, so an invalid entry cannot register partial capacity.
- An omitted filter means the instance's spell list; an explicit ID set restricts the group to those spells, including spells outside the ordinary list. An explicitly empty set admits nothing. Filter IDs are normalized but not resolved against the currently minimal catalog. Grant/filter validation completes before insertion; duplicate grant IDs and normalized filter IDs are rejected. Prepared casting enforces filter and repertoire membership and delegates effective level/list resolution as described below.
- `slotPools()` provides read-only access to the registered groups. Owners add/remove through `ResourceManager`, not through a mutable accessor. Removing and adding the same ID replaces the entire multilevel group, without affecting other groups or instances. `SpellSlotId` identifies group, spell level, and zero-based index. The shared filter only controls membership; spell-level compatibility is checked by `prepare()`, not by grant registration.
- User decision: replacing a group on level-up resets that group's consumption and preparations rather than preserving them. The base calls a noexcept removal hook before erasing a valid group; the prepared variant erases all associated state. Re-registration starts with free slots, including after shrinking and later expanding the group. Mutable slot state is persisted through the container; slot grants remain source-owned. No automatic daily recovery or declarative JSON effect is implemented.
- Tests cover registration/removal/recreation in all three modes, instance isolation, optional versus empty filters, normalization, invalid input, duplicate endpoints/grants, wrong collection item types, and endpoint cleanup/reuse.

## Prepared slot operations

- `prepare(slot, spellId, metamagic = {})` and `prepare(slots, spellId, metamagic = {})` require existing free slots of the same level, a nonblank ID in the repertoire, membership in any explicit group filter, and a resolved spell level between 0 and 9 no greater than the slot level. Independent preparations may contain the same spell. Each preparation requires exactly the slot count calculated from the catalog school and registered cost rules; duplicate normalized slot IDs are rejected. All validation precedes state mutation; failures leave every slot unchanged.
- `consume(slot)` only accepts a prepared slot and marks the entire linked preparation consumed while retaining the spell ID. `clear(slot)` removes the entire linked preparation and frees all its slots, including consumed slots; clearing an already-free slot is idempotent. This is an explicit reset, not validation of whether daily rules permit recovery. `slotState(slot)` returns a read-only value snapshot; all four operations reject missing groups, levels, or out-of-range indices.
- By default, `prepare()` loads the definition through `SpellDefinitionManager` and reads `spellLevelByClass[spellListClass]`. Unknown catalog IDs or missing class levels are rejected; explicit filters do not invent a level. School lookup always uses the catalog, even with a level override; synthetic unknown spell IDs cannot be prepared. The optional `SpellLevelResolver(CharacterClassType, const SpellSlotGrant&, spellId) -> optional<int>` remains an override for contextual levels such as special grants. It must return the effective level or nullopt if unavailable and enforce class-list membership when the group filter is omitted. It is a read-only query and must not mutate the instance or its grants. Domain/spirit level selection is not inferred automatically from the class.
- Sparse preparation state belongs to the derived class; free slots are implicit in the registered capacities. Preparation checks and consumption exemptions can now be supplied through source-owned endpoints (below); none are inferred from the list class. No spell effects or time accounting is implemented; metamagic validates source grants, applicability and costs without resolving gameplay effects. `consume` is the explicit state operation, not a complete cast action.
- Focused tests exercise transitions, duplicate copies, higher-level slots, invalid slots, filters including empty sets, repertoire rejection, resolver failures, default catalog lookup and missing-class rejection, Adept JSON parsing, group reset and isolation.

## Prepared Data and View

- `toData()` returns `PreparedSpellcastingData`: one record per preparation with a canonical first `slot`, remaining `additionalSlots`, spell ID, consumed flag, and metamagic applications. Linked slots are sorted by ID for stable output. Free slots are implicit. Grants, capacities, filters, class-list selection, repertoire, and resolver configuration are not serialized here; this is preparation-state Data, not a complete casting save root.
- `load(data)` requires the owner to reconstruct groups and repertoire first. It replaces all preparation state only after validating every entry with the same repertoire/filter/level/cost checks as `prepare()`. Rebuild cost rules and exemptions before loading; overlapping linked preparations are rejected. Missing slots, duplicate normalized slot IDs, blank spell IDs, unavailable spells, or resolver failures leave the previous state unchanged. Empty Data clears all preparations; loading does not grant slots or learn spells. Currently incompatible saved selections fail loading rather than becoming inactive reminders.
- `toView()` returns a detached `PreparedSpellcastingView` with the selected class list and groups ordered by ID. Each group includes a copy of its grant metadata and all slots ordered by level/index, including free slots, with state, optional spell ID, prepared metamagic applications, and optional canonical `preparationSlot` identifying the shared preparation. It does not resolve descriptions or require a frontend. The snapshot remains unchanged after subsequent model mutations.
- Focused tests cover round-trip prepared/consumed state, implicit free slots, normalized IDs, atomic load rejection, empty replacement, group removal, filter metadata, and detached snapshots. The container integrates these values into sheet format 27.

## Spontaneous casting

- `SpontaneousSpellcasting::consume(slot, spellId, metamagic = {})` selects a known spell at use time. It checks an existing free slot, repertoire membership, the group's optional filter, catalog identity, resolved level, casting-phase metamagic and available source uses. It returns `MetamagicEvaluation` and does not remove the spell from the repertoire or store an association between spell and slot. Ordinary spontaneous casting is not conversion; conversion-only metamagic grants are rejected.
- Default level resolution uses the chosen class-list key. The optional constructor `SpellLevelResolver` supports contextual/special-grant levels; it must enforce class-list membership for groups without explicit filters and return a level 0–9 or nullopt. Filters alone do not invent off-list levels. Unlike the prepared rules registry, spontaneous casting does not yet register a `spellLevelOverrides` endpoint; the resolver is the extension point in this slice.
- The instance registers `spellcasting.<id>.consumptionExemptions` using the existing `SpellConsumptionExemption` type. Any applicable read-only predicate preserves the slot, but metamagic source costs are still paid. No exemption is inferred from class-list selection, level zero, or spell text. Exceptions leave the slot and source balances unchanged. The registry must outlive the instance, and callback providers must outlive their entries.
- Sparse state records only consumed `SpellSlotId` values. The shared ID type now lives in `spell_slot_id.hpp`; the prepared header still includes it for compatibility. `slotState()` returns Free/Consumed. `clear()` is idempotent for existing slots, without timing gates or source-use refunds. Removing a slot group resets only that group's state; re-registering starts free. Casting instances remain isolated.
- Slot state is staged before source payment. The shared metamagic payment validates all referenced pools before decrementing; the only following state operation is a non-throwing swap. Grant/resolver/exemption callbacks must not mutate registry, slot, or pool state during evaluation. Concurrency is not supported.
- `SpontaneousSpellcastingData` contains only sorted consumed slot IDs. `load()` validates and normalizes all IDs, rejects duplicates or missing slots, and replaces state atomically. It needs reconstructed groups, not repertoire or spell definitions, and neither pays nor replenishes source uses. Empty Data clears consumption.
- `toView()` snapshots class-list selection, group/filter metadata, and every slot's state ordered by group/level/index. No spell ID/metamagic selection is attached to a slot; those are transient in the consume result. The container persists repertoire and consumed state; grant reconstruction, source pool persistence and actual spell effects remain separate work.
- Focused tests cover known-spell and filter checks, missing class levels, custom resolver failures, invalid slots, repeated use and clear, group replacement, Data/View and atomic load rejection, casting/preparation/conversion metamagic separation, insufficient uses, exemption failures, instance isolation, and endpoint cleanup/constructor rollback. Sheet suite: 65 tests passing; play tests excluded.

## Flexible casting

- `FlexibleSpellcasting` keeps preparation positions and casting slots independent. `spellcasting.<id>.preparationSlots` accepts `SpellSlotGrant` with the same validated level capacities and optional spell filter as the base `slots` endpoint. Matching IDs in the two collections are independent; no Intelligence bonus or class progression is inferred.
- `prepare(preparationId, spellId, metamagic = {})` checks a free preparation position, repertoire, catalog/filter/level and preparation-phase metamagic before paying source costs and storing the snapshot. `clearPreparation(preparationId)` frees only that position. Preparation does not require an available casting slot.
- `consume(slotId, preparationId, metamagic = {}, mixingPermissionId = nullopt)` casts the selected preparation, checks the casting group's filter and compatible base level, evaluates additions, and consumes only the casting slot. The prepared selection remains reusable. `clearSlot(slotId)` restores only that casting slot. Neither clear operation refunds source uses or imposes timing restrictions.
- `spellcasting.<id>.metamagicMixingPermissions` accepts `MetamagicMixingPermission` entries with ID/source, a read-only context predicate, and optional source usage cost. Combining preparation and casting metamagic requires an applicable permission; without a selected ID only free permissions are considered. Paid permissions must be explicitly selected. Duplicate metamagic types remain forbidden. A permission does not itself grant any metamagic application.
- The instance also owns `consumptionExemptions`. Exemptions preserve casting slots but not source uses. All checks and allocations precede one atomic payment of casting and mixing costs; exceptions leave state and balances unchanged. Preparation costs are not repaid on casting. Callbacks must be pure; concurrency is unsupported.
- An optional constructor `SpellLevelResolver` supports special levels, with the same contract as spontaneous casting. Casting and preparation groups must resolve the same base level. Flexible casting does not yet expose the prepared variant's level-override/check/cost registries or linked multi-position preparations.
- `FlexibleSpellcastingData` saves preparation IDs, spell IDs and metamagic applications, plus consumed casting slot IDs. `load()` validates both collections before replacing either, with no source payment/refill; reconstruct grants and repertoire first. View snapshots show both collections, including free positions. Removing a preparation group clears only its selections; removing a casting group clears only its consumed state.
- [Arcanista](https://golarion.altervista.org/wiki/Arcanista) is the reference for separate preparation/casting capacities, reusable preparations and the metamagic mixing restriction. The generic paid-permission hook can represent Metamix's resource cost, but no exploit, reservoir, class progression or casting-time modification is automatically implemented.
- Focused tests cover independence, repeated casts, filters/levels, free/paid/denied mixing, atomic payment failures, throwing callbacks, Data/View/load rejection, removal, isolation and endpoint rollback. The container integrates flexible state into sheet JSON; concrete providers and cast effects remain pending.

## Preparation cost rules

- `SpellPreparationCostRegistry` is an independently testable, non-copyable/non-movable component scoped by casting ID. It registers `spellcasting.<id>.preparationCostRules` and `spellcasting.<id>.preparationCostExemptions` with the sheet ResourceManager. The manager must outlive the registry; destruction unregisters both endpoints, and constructor failure rolls back only the endpoint it registered.
- `SpellPreparationCostRule` has source-owned ID/source, a `SpellSchool` selector, and a positive `requiredSlots`. `SpellPreparationCostExemption` has its own ID/source and targets an exact rule ID. Exemptions may precede their target and remain effective if that same rule ID is removed/re-added. Removing an exemption restores the rule unless another exemption targets it. These are reconstructed contributions, not persisted preparation state.
- `calculate(school, spellLevel)` returns the unchanged minimum slot level and the maximum of 1 and all applicable non-exempt slot requirements. Requirements are minimum counts, not additive surcharges; insertion order cannot change the result. An exemption disables only its target, not other requirements for the same school. This intentionally narrow implementation does not yet represent arbitrary cost formulas, slot-level adjustments, elemental-school lists, metamagia, or slot splitting.
- The opposition-school case is a rule requiring 2 slots for the selected school; Opposition Research registers an exemption targeting that particular rule. A second opposition school is a separate rule. Specialization itself is not inferred from the selected class and no school field was added to Spellcasting.
- `PreparedSpellcasting` owns its registry and registers both endpoints automatically; no concrete school rule is added automatically. `prepare()` consults the registry before committing a single linked preparation. Changes to rules/exemptions affect future preparations and loads, not existing state. Removing any participating slot group clears the entire preparation, including its slots in other groups. Data/View preserve linkage. Integration tests cover counts, same-level requirements, duplicates, filters, occupancy, consumption/clear, cross-group removal, atomic loading, and exemptions.
- Tests cover ordinary/opposition/exempt costs, unrelated schools and instances, level 0, maximum composition, multiple exemptions, reversed registration order, normalization, invalid input, duplicate registration, endpoint cleanup, and constructor rollback.
- Rules references: [Mago: Scuola Arcana](https://golarion.altervista.org/wiki/Mago#Scuola_Arcana), [Ricerca Opposta](https://golarion.altervista.org/wiki/Mago/Scoperte_Arcane#Ricerca_Opposta); English reference linked by Golarion: [Arcane Discoveries](https://www.d20pfsrd.com/classes/core-classes/wizard/arcane-discoveries).

## Preparation rule endpoints

`PreparedSpellcasting` now owns `SpellPreparationRules`, registering five additional typed collections under `spellcasting.<id>.`. Each entry has a stable source-owned ID and source; removing it restores the behavior provided by the remaining entries. Construction rolls back only owned endpoints on collision; destruction unregisters them. No class/feat effects, effect JSON parser support, or persisted callbacks are added here.

| Endpoint suffix | Entry | Behavior |
| --- | --- | --- |
| `spellLevelOverrides` | `SpellLevelOverride` | Supplies a level 0–9 for one group/spell pair; takes precedence over the constructor resolver/catalog. Matching equal values coexist; conflicting values reject resolution, independent of insertion order. |
| `preparationChecks` | `SpellPreparationCheck` | Read-only predicate receiving class-list, definition, group, slot, and resolved spell level. All non-exempt checks must succeed for every participating slot. |
| `preparationCheckExemptions` | `SpellPreparationCheckExemption` | Conditional exemption targeting exactly one check ID. Any matching exemption suffices; it can precede the check. Does not waive repertoire, filter, free-slot, level, or slot-count invariants. |
| `consumptionExemptions` | `SpellConsumptionExemption` | Read-only predicate receiving class-list, definition, and all linked slots. Any applicable exemption leaves the whole preparation prepared when `consume()` is called. Free/consumed preparations are still rejected. |

- Level overrides may grant off-list eligibility within the specified group, but do not learn the spell or bypass explicit filters. Providers must identify the intended group and register the actual special-grant level; the engine does not guess a domain from the list class. Removing a group does not remove independently owned rules: its stable ID can be re-registered.
- Checks can query live ability scores or book availability through captured providers; providers must outlive their entries. Context references/spans are only valid during the call. Callbacks must not mutate casting state, grants, or registry entries during evaluation. Exceptions leave preparations unchanged; predicates must be pure, with no dependence on evaluation order.
- `prepare()` applies operational checks. `load()` restores prior state, so it intentionally skips these checks (e.g. a currently missing book does not erase a saved preparation), while retaining repertoire/filter/level/cost/overlap validation. Reconstruct level overrides and cost rules before loading. Rule registration/removal does not retroactively alter saved preparations.
- Ordinary `consume(slot)` queries current consumption exemptions, not preparation checks. A future casting operation must separately enforce casting restrictions; these hooks do not yet implement casting eligibility or a full at-will class feature. Tests use a synthetic at-will grant on the existing fireball fixture, not a new catalog spell.
- Focused integration tests cover special levels and removal/conflicts, atomic preparation failures, targeted and conditional exemptions, live values, restore without a book, linked-slot consumption, throwing callbacks, invalid entries, instance isolation, and cleanup/constructor rollback. Sheet test suite: 64 passing, including metamagic integration; play tests excluded.

## Spontaneous conversion

- `consume(slot, std::optional<std::string_view> replacementSpellId = std::nullopt, const std::vector<MetamagicApplication>& metamagic = {})` preserves the ordinary call. An explicitly supplied blank/unknown ID is rejected, not interpreted as ordinary consumption. The source must be prepared; conversion consumes the entire linked preparation without replacing its original spell ID in state/Data/View. The replacement is not a new preparation or a stored cast log.
- `spellcasting.<id>.spontaneousConversions`, named by `spontaneousConversionsResource(id)`, accepts `SpontaneousConversion` entries with ID, source, and a read-only `replacementLevel(context) -> optional<int>` callback. The context contains both definitions, the list class, all linked slots, and the registered groups. `nullopt` means the rule does not authorize this conversion. Otherwise the callback returns the required replacement slot level (0–9); every participating slot must support it. Invalid returned levels or callback exceptions reject without changing state.
- Any one applicable rule may authorize the operation, but that single rule must cover the whole linked preparation. Providers own replacement eligibility and source restrictions (e.g. excluded domain groups, original-spell level limits, class-list membership). The registry does not guess a conversion list from names or descriptions. Callbacks follow the same purity/lifetime contract as other preparation rules.
- Replacement levels come from the authorizing conversion rule, not preparation filters/overrides: an authorized conversion is allowed to use a spell that could not normally be prepared in that group. Repertoire membership is not an extra automatic gate; providers enforce any knowledge requirements their specific ability has. Both IDs must still resolve in the catalog.
- Conversion is a sacrifice: normal `consumptionExemptions` are not queried on this path. They continue to apply to ordinary `consume(slot)`. No class or feat installs a conversion automatically; spell effects, general casting eligibility, and automatic timing checks remain outside scope. Conversion now also checks its casting metamagic cost before payment; the sacrificed preparation's metamagic is not inherited.
- Tests cover absent/removed/alternative rules, normalization and unknown IDs, level limits and invalid results, callback failures, whole-group restrictions, linked-slot payment, interaction with normal-use exemptions, free/consumed rejection, instance isolation, and endpoint cleanup/rollback. Integrated tests use the minimal fireball catalog; a registry test uses two distinct definition fixtures without expanding production content.

## Remaining rule extension points

The following are separate small steps, not empty endpoints pretending to implement unavailable operations:

- User decision: the player decides when to prepare, clear, or recover slots. Do not implement time/rest/recovery-window enforcement in the sheet. Timing-changing abilities may be informational; they are not a missing prerequisite for this subsystem.
- Concrete class/feat conversion providers remain pending; the `spontaneousConversions` infrastructure is implemented below. Casting metamagic is supported during conversion; concrete providers remain absent.
- Further metamagic cost exceptions and casting-time effects (basic eligibility/level/payment are implemented): [Spell Perfection](https://golarion.altervista.org/wiki/Incantesimo_Perfetto) demonstrates why these must be distinct. A level override is not a metamagic implementation.
- Casting eligibility/components, casting time, caster level, save DC, concentration, and spell-resistance checks belong to the future casting query/action. [Spell Focus](https://golarion.altervista.org/wiki/Incantesimi_Focalizzati) modifies save DC; it must not modify the level or slot cost. Reuse the sheet's existing modifier machinery where appropriate, preserving stacking/source rules rather than introducing a generic arithmetic callback pipeline.

Preparation examples were checked against [Cleric](https://golarion.altervista.org/wiki/Chierico) (ability requirement, domains, orisons), [Wizard](https://golarion.altervista.org/wiki/Mago) (book, cantrips), and [Spell Mastery](https://golarion.altervista.org/wiki/Padronanza_degli_Incantesimi) (specific book-check exemption). Casting-only restrictions such as cleric alignment must also be checked by the eventual casting operation, not assumed covered by preparation. English references linked by Golarion: [Cleric](https://www.d20pfsrd.com/classes/core-classes/cleric), [Preferred Spell](https://www.d20pfsrd.com/feats/general-feats/preferred-spell), [Spell Perfection](https://www.d20pfsrd.com/feats/general-feats/spell-perfection).
