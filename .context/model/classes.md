# Class Definitions

Read this document when working on class definitions, feature progression, or the future per-character class runtime.

## Implemented

- `class_definition.hpp` defines data-only `ClassDefinition`: existing `CharacterClassType` identity, Italian name/description, closed `ClassHitDie`, base skill ranks per level, typed class skills, numerical level table, and features. Each table row contains the total class BAB and base saves at that level, not incremental bonuses. The table is not fixed to twenty levels. Feature unlocks are not duplicated in this table.
- `class_feature_definition.hpp` defines features with stable IDs and level thresholds (`ClassFeatureProgressionDefinition`). Each acquisition has an ID unique throughout its class definition, effects, choices, and optional `replaces` references to other acquisition IDs. Threshold benefits are cumulative unless explicitly replaced; replacement suppresses the referenced acquisition, including its choices and descendants. Replacement chains also suppress earlier predecessors, preventing a later upgrade from reviving the original acquisition.
- Choice options own progressions of the same shape, including further choices. Their thresholds refer to the owning class level, not time/levels since choosing the option; a selected branch is eligible only while its parent acquisition is active. Recurring selections use distinct acquisition IDs; choice IDs are local to their acquisition, option IDs to their choice, and effect IDs to their acquisition. Feature IDs also remain stable for future whole-feature archetype changes.
- `CharacterClass(ResourceManager &, id, ClassDefinition, level = 1)` owns a definition snapshot, its class level and choices. It is noncopyable/nonmovable. `setLevel`, `selectOption` and `unselectOption` apply only active effects, including nested selected branches. Incomplete choices are allowed up to `selectionCount`; duplicate/unknown options and edits to inactive acquisitions are rejected. Inactive selections are retained across level decreases and branch changes. Level zero deactivates the class; positive levels must have an explicit table row.
- Scaling effects bind the exact `@classLevel` token to the instance-specific `@class.<id>.level` target, including modifier conditions, movement expressions, nested structural/casting effects, requirements and routine progression expressions. Instance IDs contain only letters, digits, underscores and dots. BAB and base saves use stable contributions backed by instance-specific targets; class skill grants use the existing typed collection. Unchanged registrations are preserved as levels/choices change.
- The runtime validates level rows, acquisition/choice/option/effect identity, choice capacity, replacement references and dependency cycles before activation. A transition applies new effects before removing obsolete effects; failed additions are cleaned up and the old level restored without removing old selections/counters. This deliberately rejects transitions requiring simultaneous ownership of an exclusive endpoint rather than destructively rebuilding old state. Cleanup callbacks must remain nonthrowing, as for other source runtimes.
- Resources and their owning subsystems must outlive `CharacterClass`. Destruction removes effects in reverse order, then owned targets; `ResourceManager::unregisterTarget` supplies the missing target lifecycle operation. Failed construction cleans up registered targets and applied additions.
- The focused schema test covers numerical rows, typed fields, nested option progression, additive and replacement metadata, independent recurring choices, and deep value copies. Fixtures are synthetic, not a class catalog.
- `ClassDefinitionManager` owns an immutable typed catalog supplied as a vector of definitions, rejects duplicate/unknown class types, and returns stable const references by `CharacterClassType`. Its singleton catalog is intentionally empty until actual content is supplied; it does not yet parse a JSON file. Runtime structural validation still belongs to `CharacterClass`.
- `Classes(ResourceManager &, const ClassDefinitionManager &)` owns one `CharacterClass` per enum value. `addLevel(type)` loads a definition and creates level 1 on first acquisition, then increments the existing instance. Undefined next levels and failed initial application leave the container unchanged. `level()` computes the sum (zero when empty); `CharacterClass::level()` supplies each value. Selection methods forward by class type without exposing mutable instances.
- `characterClassId(type)` maps all current enum values to explicit stable English IDs, independent of enum ordinal values and Italian display names. Container-owned instances use these IDs, producing targets such as `class.wizard.level`. There must be only one Classes container per ResourceManager; the registry, endpoint owners and definition manager must outlive the container.
- Container tests use synthetic catalogs and cover first/subsequent acquisition, independent multiclass totals and contributions, retained choices, missing/max-level errors, constructor rollback, destruction cleanup and manager lookup behavior.

## Next Steps and Boundaries

- The sheet exposes only one-step advancement operations: `addClassLevel(type, hitDieResult)` and `removeClassLevel(type)`; `Classes` provides corresponding `addLevel`/`removeLevel`. Removing a level discards its die and favored-class bonus, updates effects and total-level feat slots, and removes the class instance when it reaches zero. Other class levels are unaffected. Low-level `CharacterClass::setLevel` and loading remain implementation/restoration mechanisms, not sheet APIs.
- User decision: advancement requires completing the current level's mandatory choices, including initial race, alignment and favored-class selection. Feat selection/retraining checks the current sheet, not historical reconstructed states. `CharacterSheet::addClassLevel` uses the shared pending-choice report and rejects blocking entries before applying any changes. The gate does not apply to -1 or saved-state reconstruction. See [pending choices](pending-choices.md) for the agreed policy and typed references. Existing inactive feature choices remain retained while their class instance exists; removing its last level discards that instance's choices/archetypes.

- `CharacterSheet` now owns Classes after effect consumers, delegates public `level()` to its sum, and exposes `addClassLevel`, `selectClassOption`, and `unselectClassOption`. A new sheet has level 0 and no base feat slots. Level changes update odd-level feat slots and recheck prerequisites; class choice changes also recheck prerequisites. Both construction and `load(path, catalog)` can receive an immutable class manager; it must outlive the sheet. The default catalog is still empty, so real definitions must be supplied until catalog content/loading is implemented.
- Format 30 persists class type as a stable English ID, level and choice acquisition/choice/option IDs only. Inactive choices are retained. Class definitions, effects, derived totals and callbacks are not serialized. `CharacterClass::load` validates selections without requiring them to be active; `Classes::load` restores only into an empty container and rolls back all created instances if any fails. The sheet reconstructs classes before loading feat selections and granted-spell/casting state. Unknown types, missing definitions, duplicate classes/choices/options and invalid levels are rejected, not silently dropped.
- Pre-30 saves have no class identity to recover. They load with no classes and level 0. If they contain a selected `base.feat.level1`, a persisted `legacyFirstLevelFeatSlot` compatibility flag keeps that slot/selection until the first actual class is added, then disappears without duplicating the slot. The flag is exposed in CharacterSheetView so a future UI can explain the pending class assignment. It does not invent class levels or bonuses; other level-dependent values reflect level 0 until assignment.
- `CharacterClassView` exposes type/name/level and feature descriptions with flattened acquisition snapshots, their parent acquisition/choice/option IDs, level thresholds, active state, all options, selected flags and remaining selection counts. `ClassesView` contains the total level and class list; it is included in CharacterSheetView. Snapshots retain inactive selections. No separate catalog-selection View has been added.
- Focused tests cover sheet multiclass totals, base feat progression, source-owned feat/spell restoration, consumed spell uses, inactive choices, deterministic JSON round trips, malformed saves and legacy feat migration. Catalog content and definition JSON loading remain deferred.
- `addClassLevel(type, hitDieResult)` / `Classes::addLevel` accept a raw player-supplied die result, validated against the definition's hit die. Omitting it preserves an incomplete level (including legacy migrations), without inventing a roll. `setClassHitDieResult(type, classLevel, result)` corrects/fills a one-based class-level result. Data and View expose the sparse `hitDieResults` map; reducing a standalone runtime's level discards rolls above the new level. Failed advancement restores both level and rolls.
- Each class adds its dice to `hp.max`, plus a correction ensuring at least one HP per supplied die after Constitution. The existing global Constitution contribution remains counted exactly once. Maximum changes preserve damage taken. First-level maximization/rolling conventions remain player-owned; racial Hit Dice remain unsupported. Missing rolls mean HP are incomplete; existing legacy `baseMax` is retained, not silently converted into rolls.
- Each class contributes `level * max(1, skillRanksPerLevel + @intSkillRanksMod)` to the accumulated `skill.ranks.max` endpoint owned by Skills. Independent source-owned contributions (including ordinary declarative contribution effects) add extra ranks after the class minimum. `SkillsView` reports maximum, spent and remaining ranks, including specializations; a negative remainder reports overspending without deleting ranks. This is the total budget, not the per-skill rank limit. No automatic allocation or new setter restrictions were introduced.
- Intelligence for the freely allocatable budget uses `@intSkillRanksMod`, recalculated on changes and excluding temporary contributions plus modifiers marked `SkillRankBudgetPolicy::Excluded` before stacking. Permanent and temporary contributions still obey ordinary cross-endpoint stacking for the total score. Source-owned rank grants now support fixed or computed quantities separately from invested ranks. Headband-style effects can exclude their Intelligence contribution from the free-rank budget while granting ranks separately; concrete catalog providers remain pending. By user decision these item bonuses are permanent immediately; no 24-hour timer is required. Favored-class eligibility/reward choices are implemented in [favored-classes.md](favored-classes.md); general advancement history remains deferred. Spell progression and caster level remain distinct and source-owned; do not recreate a casting instance at every level-up. `spellcastingGrant` now creates/removes a casting through the shared effect pipeline. Keep this grant on a stable acquisition; `spellSlotGrant` supplies multi-level casting/preparation groups using the target casting's explicit runtime ID. Slot tables/progression are source-owned; replace only the slot acquisition when advancing, not the stable casting grant.
- Format 32 adds `hitDieResults` as an array of `{level, result}` records per class. Parsing rejects duplicates, out-of-range levels and non-integral results; runtime load additionally checks the class's die size. Pre-32 saves have no supplied dice. Totals and skill-rank contributions are reconstructed rather than persisted. Focused advancement tests cover multiclass floors, ability changes, retained wounds, correction, source bonuses, overspending, malformed saves, rollback and migration.

- Archetypes support typed definitions/catalog lookup, compatibility checks, addition/removal through Classes and the sheet, structural feature edits, shared choice APIs, View and format-31 persistence. Removal resets choices on restored original features and forgets the removed archetype's choices. See [archetypes.md](archetypes.md) for validation, rollback and lifecycle semantics.
- Requirements for individual class options and reusable option catalogs remain future work; do not treat all class-feature selections as feats.
- Keep the next implementation step narrow and agreed with the user.

## Advancement Rules References

- [Intelligence](https://golarion.altervista.org/wiki/Intelligenza): signed modifier, minimum one rank per level, temporary/permanent distinction.
- [Fast Learner](https://golarion.altervista.org/wiki/Apprendimento_Rapido): both HP and rank favored-class rewards, not an Intelligence replacement.
- [Cunning](https://aonprd.com/FeatDisplay.aspx?ItemName=Cunning): extra rank per Hit Die, including existing HD; verified in the English archive because no matching Golarion feat page was located. Neither feat is added to the catalog in this step. No feat replacing Intelligence for the rank budget was found in this check; this is not a proof that none exists.
