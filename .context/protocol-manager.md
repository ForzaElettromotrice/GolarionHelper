# ProtocolManager

Status: C++20 implementation/tests updated, 2026-11-12. ProtocolManager owns connections, SessionCode, identity archives, JSON join/resume, authenticated command dispatch, TCP hosting, and a worker. Session remains a facade. Client-side ProtocolManager, concrete role/sheet commands, and user-list events remain future work. See `session-protocol.md`, `session-admission.md`, and `session-commands.md`.

## API and ResourceManager Integration

- `ProtocolManager(ResourceManager &resources)` first registers `session.join` and `session.resume` through `add_command`, both with minimum `Role::Any`, then publishes only `protocol.add_command` in Session's ResourceManager. Its exact signature alias is `ProtocolManager::AddCommandSignature = void(std::string_view, Role, CommandCallback)`. Registering the built-ins first makes duplicate checks protect both names, including padded variants, without a separate routing namespace.
- `add_command(std::string_view name, Role minimumRole, CommandCallback callback)` stores a unique command name, its minimum role, and a copyable callback. Names are case sensitive with outer ASCII whitespace trimmed. Empty names, duplicate names, invalid enum values, and empty callbacks throw `std::invalid_argument` without replacing an existing command.
- `dispatch(std::string_view name, const CommandContext &context, const nlohmann::json &payload) const` returns the callback's JSON result. It remains a direct C++ method, not a ResourceManager feature, and the wire handler reuses it. Payload must be an object; supplied ConnectionIds must still match the active UserId. Invalid contexts, unknown commands, failed role checks, and insufficient roles reject before callback execution.
- `CommandCallback` is `std::function<nlohmann::json(const CommandContext &, const nlohmann::json &)>`. It may return any JSON value, including null for an operation with no result. Mutable callback state persists between calls; callbacks may register other commands or perform nested dispatch.
- Every dispatch, including Any commands, invokes `roles.hasAtLeastRole` using `RoleManager::HasAtLeastRoleSignature` with an optional UserId. A live anonymous connection satisfies only Any; registered users satisfy their current threshold and lower ones. Any cannot be assigned to participants. Permissions are read at execution time, so promotions/demotions apply immediately. Unknown supplied identities and missing or incompatible role lookup features reject the request. Target-specific authorization remains in the subsystem mutation operation, such as `roles.setRole`.
- Dispatch failures use typed `ProtocolError`/`ProtocolErrorCode`, compatible with existing `std::invalid_argument` catches. Callback exceptions propagate unchanged through direct calls. The wire handler maps typed failures, invalid payload/JSON access, and other exceptions to shared rejections; individual callbacks validate payload fields and domain permissions. See `session-commands.md`.

```cpp
resources.invoke<ProtocolManager::AddCommandSignature>("protocol.add_command", "example.echo", Role::Player, [](const CommandContext &context, const nlohmann::json &payload)
{
    return nlohmann::json{{"sender", *context.userId}, {"data", payload}};
});
const auto result = protocol.dispatch("example.echo", verifiedContext, nlohmann::json{{"value", 3}});
```

## Command Context and Trust Boundary

`CommandContext` contains `std::optional<UserId> userId` and `std::optional<ConnectionId> connectionId`, both defaulting to `nullopt`. A live pending connection has a ConnectionId without a UserId. A trusted local call supplies a known UserId without a ConnectionId; a context with neither is rejected. `ConnectionId` aliases `std::uint64_t`; ProtocolManager allocates logical IDs and its private Hosting implementation owns sockets. There is no cached role or secret token in the context.

ProtocolManager implements `registerConnection`, `bindUser`, `getUserId`, `makeContext`, and `closeConnection`; see `session-protocol.md` for their behavior. Session retains delegating methods for all except `getUserId`. `makeContext` checks actual logical-record existence and both directions of a binding; it never treats a missing record as an anonymous connection. `getUserId` remains a direct ProtocolManager lookup for Hosting; no connection feature is published through ResourceManager.

Build context at execution time. Returned values are detached, and dispatch revalidates any ConnectionId/optional-UserId pair before use. Closed/replaced records and cached anonymous contexts that have since been admitted are rejected. JSON admission callbacks verify code/token before binding; `bindUser` checks ID/association invariants. Local contexts without ConnectionId remain trusted application calls. Hosting routes every command, including join/resume, through `makeContext` and the same dispatch; payload fields cannot override the actor. Replacement/close and callback execution are serialized.

## Session Code

ProtocolManager initializes a const SessionCode candidate during construction. `getSessionCode()` returns a detached string for Session's display delegation, and `verifySessionCode(candidate) noexcept` performs strict five-character ASCII comparison with lowercase accepted. The host console displays the code. Start/stop never regenerate it, and concurrent reads require no code-state lock because the manager never changes it. No code feature is published through ResourceManager.

The user deferred the host-wide registry/collision checks and code persistence; identity restoration does not restore the code, and there is no code uniqueness guarantee yet. JSON join/resume verifies the current candidate. See `session-protocol.md` for SessionCode's exact value/validation contract and tests.

## Hosting Lifecycle

- `std::uint16_t startHosting(std::string_view bindAddress, std::uint16_t port)` is called directly or through Session's delegation. It opens a numeric IPv4 listener and starts a dedicated worker; the return value is the actual listening port (`0` requests an OS-assigned port). Bind/listen/thread-creation failures propagate synchronously and release partial resources without clearing existing logical state. Starting an already-active host throws `std::logic_error`.
- `void stopHosting()` serializes against start/stop, requests shutdown, joins the worker, releases sockets, and clears connection/binding maps while preserving the ID counter and RoleManager data. Calling it while inactive does nothing. Unrecoverable worker errors are captured and rethrown by explicit stop after cleanup; destructors suppress them.
- Stop checks run before each buffered peer, before select, and in the shared input processor. Immediately before `handleMessage`, the worker acquires the existing execution mutex and rechecks stop, so a request waiting behind local execution is discarded too. A request already past that final checkpoint may finish; pending buffers are discarded during socket cleanup, and delivery of its final response is not guaranteed. Stop does not forcibly cancel callbacks or disable trusted local dispatch. See `session-commands.md` for the execution boundary.
- The private nested `ProtocolManager::Hosting` lives in `src/hosting.hpp`/`src/hosting.cpp`; its implementation hides platform sockets, buffers, and the thread. There is no public polling API, transport getter, or hosting feature in ResourceManager.
- Accepted sockets get fresh logical ConnectionIds. Peer failure/timeout closes the socket and removes its logical record. The worker also closes sockets whose logical records were removed/replaced by trusted local operations. It uses nonblocking sockets and a select wait capped at 50 ms, so idle peers, partial frames, and peers that do not read cannot block shutdown.
- Hosting forwards messages to private `handleMessage` in `src/admission.cpp`, which validates requestId and calls `handleCommand` for every name. Dispatch selects the registered callback, including join/resume. All successes use `request.accepted` with `payload.result`; rejection building is shared. Pending expiry, buffers, and the 32-peer cap remain unchanged. Successful generic Any commands keep a pending peer anonymous without resetting its deadline. Command errors close pending peers but retain admitted peers; framing/stale-context failures close either. Encoding an invalid/oversized callback result produces `COMMAND_FAILED` without retry. See `session-admission.md` and `session-commands.md`.

## Tokens and Identity Archives

ProtocolManager owns private `detail::UserTokens` and exposes `issueUserToken`, `resolveUserToken`, `saveIdentityState`, and `loadIdentityState`. Session delegates issuance/save/load and user registration, keeping lookup only on ProtocolManager. No token feature is published through ResourceManager. Tokens contain eight random bytes encoded as 16 lowercase hex characters; OpenSSL Crypto generates them and hashes their raw bytes with SHA-256. There is no SessionId.

The archive stores UserIds, roles, and digests, never original tokens. Issuance requires an already saved/loaded archive and saves the candidate before returning the credential. Duplicate issuance is rejected. Later role/registration changes need an explicit save. Existing files must be loaded before replacement; restoration requires hosting stopped and the same immutable Host UserId. Successful load replaces roles/tokens and clears logical bindings without resetting their ID counter or changing SessionCode. See `session-tokens.md` for the exact schema, validation, failure behavior, and tests.

Define its API and integration with Session then; no replacement client executable is present now. The host remains authoritative for admission and roles. Useful observations from the removed client, including the Linux send-timeout ordering, are archived in `history/2026-11-10-game-network-prototype.md` and must be revalidated for the new implementation.

The host console creates `Session("host")`, creates/loads the optional identity archive (default `session-identities.json`), calls startHosting, and keeps its main thread alive with a short sleep until Ctrl+C. That wait does not process network events. It then explicitly stops hosting; Session destruction also guarantees stop before subsystem teardown.

## Ownership and Lifetime

- Session owns ResourceManager, ProtocolManager, and RoleManager in that order. It contains no connection state or connection feature registration. Its destructor stops hosting before provider teardown; ProtocolManager also stops its worker before unregistering `protocol.add_command`. ResourceManager outlives providers, and application code must finish local calls before destruction. Role checks apply through the same dispatch for local and remote calls, without subsystem getters.
- ProtocolManager cannot be copied or moved because its registered feature refers to its address. It owns `protocol.add_command` for its lifetime; other subsystems must not remove or replace that feature. A constructor collision leaves the existing registration intact. Destruction unregisters the feature and releases all callbacks.
- There is no command removal operation. A recursive execution mutex serializes registration, local/remote dispatch, admission, binding, and close, preserving nested registration/dispatch and callback state. Connection/role locks are released before invoking command callbacks. Join locks execution, identity, connections, then roles; load adds lifecycle before execution. Stop joins without the execution lock and takes it only for final cleanup. Lifecycle/load calls from callbacks are rejected before locking, avoiding self-join and lock cycles. Fixed registry features/providers must outlive the worker; arbitrary provider access outside dispatch retains its own synchronization contract. See `session-commands.md`.

## Dependency and Verification

The public payload/callback API uses `nlohmann_json` 3.12, already required by the sheet module. `golarion_play` links its CMake target publicly and `Threads::Threads` and `OpenSSL::Crypto` (3.0+) privately, plus ws2_32 on Windows, and remains independent of `core/sheet/` and the frontend. The standalone play build requires both JSON and OpenSSL Crypto. Token and archive coverage is documented in `session-tokens.md`.

`play_protocol_manager_test` passes with native GCC C++20 and warnings treated as errors. It covers JSON results/context forwarding, direct and registry registration, all 16 participant minimum-role combinations, anonymous Any dispatch, protected built-in names/padded variants, invalid registrations/payloads/users, sender fields in payloads, immediate permission changes, RoleManager's target-specific protection, missing role services including Any, constructor collision and destruction, nested dispatch while adding commands, callback state/exceptions, independent instances, and Session construction. Connection coverage includes pending/unique IDs, binding validation/idempotence, replacement, stale requests/disconnects, stale anonymous contexts after admission, detached lookups/contexts, and fresh-context dispatch with current roles. It also verifies the code getter, lowercase acceptance, and rejection of different/malformed candidates. The rebuilt Session delegation/isolation suite and RoleManager suite also pass. CMake is not installed in the local environment, so its configuration remains unexecuted; manual compilation used the official 3.12.0 single header cached under the ignored `build/play/dependencies/include/` directory.

`play_hosting_test` passes on Windows with native GCC C++20, strict warnings, and pthread support. It covers Session delegations, multiple real TCP peers, fragmented/invalid frames, correlated pending unknown/forbidden rejections without invoking protected callbacks, startup rollback, duplicate/occupied listeners, stop/restart, stable session codes across that lifecycle and startup failure, prompt shutdown, concurrent lifecycle/logical-state operations, role retention, and automatic cleanup of both Session and standalone ProtocolManager. Admission tests add anonymous Any dispatch and common join/resume results. Loopback execution requires local socket permissions in this environment; the sandbox blocks connects with WSA error 10013. CMake and the POSIX branch remain unverified locally.

The buffered-stop correction is covered by two additional cases in the existing admission suite: stop during the first of two peers' buffered callbacks, and stop while a remote request waits behind a local callback. Both fail against the previous library and pass against the correction. Admission, hosting, ProtocolManager, identity-persistence suites, and the real host restart smoke test pass in `build/play/stop-buffered/`; no public API or CMake target was added.
