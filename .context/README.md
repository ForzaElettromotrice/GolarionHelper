# GolarionHelper Context

## Project Goal

Build a local-first native desktop tabletop role-playing application in C++, expanding toward a virtual tabletop in the style of Roll20. The implemented rules engine remains Pathfinder 1e; support for another ruleset is not implied.

## Current State

- `main` is the default development and GitHub branch. The game-host feature branch is `feat/game-host`; the previous `master` branch is retained separately.
- The C++20 backend, persistence, Views, and a minimal opaque-handle C API are in place; frontend work remains deferred.
- `core/` groups backend modules. The character-sheet engine lives in `core/sheet/`. The independent `core/play/` C++20 module provides the Session model and a separate real TCP host/client prototype with synchronized connected-participant lists and diagnostic console tools. The prototype's model/protocol tests and process-based loopback test pass. Its network role integration, sheet bindings, persistence, authentication, and frontend remain future steps; see `game-management.md`. In-app chat/voice/video are outside scope.
- `golarion::play::Session`, the main play aggregate, now requires an explicit host user ID and owns ResourceManager plus RoleManager, passing the registry by reference. RoleManager enforces immutable host/master/player/spectator permissions and publishes `roles.registerUser`, `roles.getRole`, `roles.hasAtLeastRole`, and `roles.setRole`; focused tests pass. See `session-roles.md`. Server ownership and connected-user management remain future steps.
- The session ResourceManager lives in `core/play/` and implements typed function registration, invocation, and removal, with focused C++20 tests passing. Each Session has an independent registry. See `architecture.md` for the API and lifetime rules; the sheet-specific `golarion::ResourceManager` retains its existing responsibilities.
- Declarative `EffectDefinition` values and `compileEffect` are shared by source subsystems. The six-point backend audit now has typed JSON bridges for structural/casting endpoints and feat prerequisite alternatives, recursive class-level binding, selective CA retention, bounded movement bonuses and sheet inventory/casting operations. See [`model/effect-endpoints.md`](model/effect-endpoints.md) for coverage and boundaries.
- `CharacterSheet` owns `Classes`, with enum-based level advancement and a computed total (initially 0). Class definitions/runtime support level-gated choices, replacements and base contributions; format 33 persists class identity, levels, player-entered hit dice, archetype IDs, favored-class selections and feature choices before reconstructing dependent state. Class Views are exposed by the sheet. `ClassDefinitionManager` supplies immutable typed definitions (default catalog empty); definition JSON/catalog content remain deferred. See [`model/classes.md`](model/classes.md).
- `RaceDefinitionManager` loads the embedded catalog of all seven core races, while the per-character `Race` runtime applies effects, manages alternate features and choices, persists configuration, and exposes `RaceView`. Standard traits use supported effects and explicit situational bonuses; unsupported mechanics remain reminders. Umano also retains Doppia Dote.
- `FeatDefinitionManager` loads immutable feat definitions from embedded JSON. `CharacterSheet` owns `Feats` with source-owned slots, prerequisite alternatives/exemptions, repeatability, choice-matched dependencies, and stable-state activation. Sheet changes automatically recheck prerequisites; manual text requirements are informational. Format 25 persists selection IDs and choices; Views expose distinct acquisitions and slots, with slot availability independent from feat activation. Source withdrawal preserves selected feats and choices, including across save/load. The minimal catalog remains Iniziativa Migliorata.
- Informational special defenses cover the planned categories, including the locally implemented energy vulnerabilities.
- Attack routines now accept source-owned conditional hand-usage permissions without reclassifying weapons. Permissions can be scoped to a strike/routine/slot and are exposed in candidate Views. The shared `handUsagePermission` effect now parses and compiles these grants with reversible cleanup; concrete providers and contextual penalty rules remain separate; see [`model/combat.md`](model/combat.md).
- Item definitions support named usage pools with capacity only; instances own independent remaining counts. `consume`, `refill` and capped `restore` do not interpret recovery rules, which belong in description text. `spellGrant` effects connect item reserves to granted spells without resetting them on equip. See [`model/equipment.md`](model/equipment.md).
- `CharacterSheet` owns `GrantedSpells` through `spells.granted`: single-spell grants support own uses, at-will, constant and shared-pool usage, source cleanup, Data/View and format-29 persistence. Actual cast resolution remains separate. See [`model/granted-spells.md`](model/granted-spells.md).
- `SpellDefinition` ports the typed Java schema from `master`: closed enums, separate class/domain/bloodline level maps, structured casting/component/save metadata, descriptive text, and explicit validation. `SpellDefinitionManager` loads an embedded JSON catalog through strict enum parsing and validation; the minimal catalog contains Palla di Fuoco. `CharacterSheet` owns `Spellcastings`: its `spellcastings` endpoint creates/removes independent prepared, spontaneous or flexible instances using source-chosen IDs. Spell definitions also accept shared declarative effects as metadata only; targeting/application and concrete casting sources remain unimplemented. The shared `spellcastingGrant` effect now creates/removes prepared, spontaneous or flexible casting instances; `spellSlotGrant` now grants multi-level casting or flexible preparation slots with a shared optional spell filter and an explicit target casting ID. Concrete progression tables remain source-owned.
- `Languages` distinguishes source grants from learned selections, persists the latter in format 26, and reports unused/exceeded quotas. `languageGrant` is supported by the effect parser/compiler. Intelligence entitlement is computed from `max(0, intPermanentMod)`; format 35 saves only learned choices and ignores the validated legacy manual quota. The `languageOptions` effect now registers per-origin selectable lists through `languages.options`; their union is enforced by `add`, and without lists no new language can be learned. Lists appear in Views and are reconstructed from sources, not saved. Concrete racial/skill lists and secret-language policies remain catalog/provider work.

## Next Steps

Continue in small, separate changes:

Sheet focus: class and archetype selection/removal, compatibility, runtime effects, persistence and Views are in place. Archetype features reuse ordinary class choice APIs; removing an archetype resets its choices and those of restored original features while preserving unrelated state. Player-entered hit dice and the class-driven skill-rank budget endpoint are implemented with persistence and Views. Favored-class choices, source-owned eligibility/bonus endpoints, cumulative rewards and their effect parser are implemented; see [`model/favored-classes.md`](model/favored-classes.md). Feat selections now survive unavailable source slots and save/load. The experimental evaluation/projection infrastructure remains removed. Feat checks now preserve valid active effects, propagate losses and reactivate eligible acquisitions through successive live passes without recursive checks. Feat-owned slots and cumulative favored-class slot rewards are supported, retaining selections when a source disappears; see [`model/feats.md`](model/feats.md). Intelligence now separates permanent and temporary modifier endpoints while stacking both together for total scores; skill-rank budgets use `intSkillRanksMod`, additionally filtering source modifiers marked excluded before stacking. Language entitlement continues to use `intPermanentMod`; source-owned skill rank grants now use the maximum of invested/granted ranks, with fixed or computed quantities, and do not spend the player's budget. Headband-style Intelligence exclusions and separate rank grants are now supported; concrete catalog JSON/content remains separate; item Intelligence bonuses apply permanently immediately by user decision, without a 24-hour timer; see [`model/classes.md`](model/classes.md) and [`model/archetypes.md`](model/archetypes.md).

Current focus: prepared, spontaneous, and flexible casting support consumption, metamagic, atomic shared-source usage payment, and Data/View. Sheet format 27 now persists casting IDs, repertoires and mutable state after source reconstruction. The sheet now owns the casting container and creation endpoint; progression remains source-owned through updates to instance endpoints, not a generic casting level. Prepared casting additionally supports linked preparations and spontaneous conversion; flexible casting separates persistent preparations from casting slots and requires permission to mix prepared and casting metamagic. No class/feat/item grants are installed automatically, and the player decides when to recover slots. Format 34 now persists historical preparations independently of revoked metamagic grants and restores shared metamagic source balances atomically. Inventory Views expose usage pools; casting Views expose available metamagic grants, costs and flexible mixing permissions. Metamagic can now reference an item's existing usage pool, with no duplicate balance or persistence. Concrete providers, special cost reductions and cast-effect/target resolution remain pending. Sheet operations now expose repertoire, preparation, consumption and clearing for all three casting modes, without exposing mutable subsystem references. Single-spell grants and item bindings are implemented; next steps are concrete catalog providers and cast resolution, one slice at a time. See [`model/spells.md`](model/spells.md) and [`model/metamagic.md`](model/metamagic.md).

1. Introduce ProtocolManager command registration and minimum-role checks using RoleManager's registered features, passing the Session-owned ResourceManager by reference. Use `session-protocol.md` to finalize detailed message schemas before network integration; server ownership, user identity/token management, and each further subsystem remain separate steps.
2. By user decision, defer migration of core-race reminders and racial language/bonus-feat connections until the complete dataset is built. Do not start catalog migration as the next backend step.
3. Await the user's next development direction. Declarative prerequisite alternatives support expressions filtered by feat type or ID; future sheet mutation APIs must maintain the feat recheck convention.
4. Keep feat catalog expansion and catalog Views deferred. The race catalog View and further alternate racial features/races remain roadmap items, to address one at a time.

## Context Structure

- [`model/README.md`](model/README.md): index of model subsystems. Start there, then read only the document relevant to the current change.
- [`architecture.md`](architecture.md): cross-cutting architectural decisions and the session ResourceManager API/lifetime rules. Read before changing subsystem registration, ownership, persistence, Views, or the C boundary.
- [`game-management.md`](game-management.md): implemented TCP presence slice, confirmed multiplayer requirements/structural decisions, and the larger proposed game lifecycle, permissions, sheet import, and recovery. Read before changing `core/play/` or planning further game management and networking.
- [`session-roles.md`](session-roles.md): implemented RoleManager API, user-ID semantics, feature signatures, ownership, and permission-test coverage. Read before changing roles or consuming `roles.*` through ResourceManager.
- [`session-protocol.md`](session-protocol.md): confirmed JSON/TCP, session-code, identity-token, and reconnection decisions, proposed admission/role messages, and remaining technical details. Read before changing the protocol or implementing the user subsystem; the new contract is not implemented yet.
- [`development.md`](development.md): local build and test commands and required packages.
- [`roadmap.md`](roadmap.md): pending model work and deferred post-character-sheet work. Read when selecting or planning the next implementation step.

Useful superseded decisions and past operational events belong in `history/` when such history first needs to be retained.
