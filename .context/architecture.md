# Architecture

- The domain model is implemented in modern C++.
- Play authorization uses PermissionSet/PermissionManager: closed flags, uint64 masks, immutable host identity and replacement presets. Permission features include staged registration and mutation commits. Host Session explicitly registers the permission RPCs; JSON v4/archives v4 use validated numeric masks. Public NoAuth remains distinct from authenticated Any. See session-permission-commands.md.
- Item/effect definitions have bidirectional JSON codecs reused by embedded catalogs and custom-item persistence. The sheet model and persistence compile into the same `golarion_model` library because the codecs reuse domain parsers and validation. See `model/equipment.md`.
- Rule categories are a closed system and must use enum classes. JSON may use stable English names, but parsers reject names outside the enum vocabulary. IDs and descriptive text remain strings. The current change aligns spell metadata and feat types/slot filters/Views; it does not silently migrate unrelated existing subsystems.
- `core/` is the backend module container; `core/CMakeLists.txt` adds `sheet` and `play`. Sheet rules, catalogs, and persistence live in `core/sheet/`; independent `core/play/` owns Session modes, the registry, and native TCP host/client.
- SessionServer owns ResourceManager, ServerProtocol, PermissionManager and SheetManager. Only SessionClient has client protocol runtime state. Both expose role-specific operations; server shutdown joins workers before its providers are destroyed.
- ClientProtocol owns ClientConnection. ServerProtocol owns logical bindings, IDs, Hosting/LocalCommands and private credentials/archive operations. Session delegates, keeping getUserId and token lookup on ServerProtocol. No separate ConnectionManager or SessionId is introduced. Authority comes from trusted bindings and current PermissionManager checks, not payload claims.
- SessionCode is an independent value type held by the ServerProtocol. Desktop campaigns persist and supply their code on reconstruction. Clients supply a remote code to join or resume. See [session protocol](session-protocol.md).
- The desktop frontend uses Qt Quick/QML for Windows and Linux. Reusable subsystem panels live outside `core/`. The local Qt controller links directly to the C++ sheet model; session-backed sheet control remains future work. See [frontend](frontend.md) and [interoperability](model/interop.md).
- Complex frontend snapshots may later be exchanged as JSON. ServerProtocol already uses `nlohmann_json` 3.12 for backend command payloads/results; frontend contracts remain undecided.
- Sheet presentation and persistence use `toView` and `toSaveData`. Play uses `toView` and `toData` on Session and campaign records. `Session` assembles the C++ value snapshots from the relevant subsystem projections. ServerProtocol supplies the host port, participants and synchronized identity data. ClientProtocol supplies client state. See [game management](game-management.md#desktop-hosted-campaigns).
- Character-sheet components register enhanceable resources by name; they neither create nor retain their `ModifierSet`.
- `golarion::play::ResourceManager` is shared only by reference among one Session's subsystems. It is separate from the sheet-specific `golarion::ResourceManager`; no sheet behavior is moved into it. Its implementation and tests live in `core/play/`.
- PermissionManager implements user registration, current-mask lookup, all-required checks, authorized flag changes/presets and validated snapshots. Host alone grants/revokes ChangePermissions; delegates cannot target self/host. Presets preserve that flag. Commit callbacks run under the manager lock and must not reenter managers; see session-permissions.md.
- ServerProtocol publishes protocol.add_command, protocol.sendEvent and trusted internal identity.updateUserPermissions. The latter coordinates synchronous candidate permission mutations with the archive/token snapshot, using execution-then-identity-then-permission locks. Client mode publishes protocol.on_event with a callback-only signature and dispatches admitted-host notifications through its event-only registry. Each Session has its own registry. Collisions roll back owned registrations and destructors join workers before unregistering providers. See session-events.md for the bounded outbox and client lifecycle references.
- The private codec implements JSON v4 independent of permissions/identity, with a four-byte prefix and 64 KiB cap. Host archives v4 store hostId, masks and tokens. Permission RPCs emit targeted permissions.changed. session.getParticipants/session.participantsChanged expose a revisioned projection of connected bindings plus the local host to admitted users, without extra permission bits. ParticipantInfo is detached public data, not a second registry; ClientSnapshot/HostSessionView carry it. Full game persistence remains separate. See session-participants.md.
- Automatic condition generation from independent character-sheet state is deliberately limited to `Barcollante`, `Privo di Sensi`, `Inabile`, `Morente`, `Stabilizzato`, and `Morto`. A condition definition may still generate another condition when the latter is a mandatory rules consequence, such as `Privo di Sensi` producing `Indifeso` or `Immobilizzato` producing `Impreparato`; the derived entry exists only while its source condition requires it. Every other character condition requires an explicit external source entry. `Impreparato` is not generated from encounter state because encounter-state integration is not implemented; a future play module may supply it, while `Rotto` is excluded because it is a condition of individual objects rather than of the character.

## Session ResourceManager

- `registerFeature<Signature>(name, callback)` owns a nonempty `std::function<Signature>` under a unique name. Callbacks must be copy constructible, as required by `std::function`.
- `invoke<Signature>(name, arguments...)` checks the exact registered signature, including return type and reference qualifiers, before forwarding arguments and returning the callback's result. Void and reference returns and move-only arguments are supported. Mutable callback state survives successive calls.
- `unregisterFeature(name)` removes the registration; the name can subsequently be reused with another signature. Calls already in progress retain the original callable until they return, including when a callback removes or replaces its own registration. Nested invocations are supported.
- Names are case sensitive, with outer ASCII whitespace trimmed consistently in all operations. Empty/whitespace-only names, empty callbacks, duplicate registrations, missing features, and signature mismatches throw `std::invalid_argument`. Callback exceptions propagate unchanged.
- Providers must outlive callbacks; finish external calls and stop both networking and local workers before teardown. ResourceManager/Session cannot be copied/moved. Finish fixed feature registration before work begins; concurrent lookup of unchanged features is supported, while registry mutation remains serialized. PermissionManager synchronizes its data and ServerProtocol serializes local/remote callbacks and registration. Independent provider access retains its own threading contract. ResourceManager does not interpret authorization, TCP or JSON.

```cpp
resources.registerFeature<int(int)>("example.double", [](int value) { return value * 2; });
const int result = resources.invoke<int(int)>("example.double", 3);
resources.unregisterFeature("example.double");
```
