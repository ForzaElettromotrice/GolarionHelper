# Architecture

- The domain model is implemented in modern C++.
- Item/effect definitions now have bidirectional JSON codecs reused by embedded catalogs and custom-item persistence. Saved custom definitions use domain parsers/validation; `golarion_persistence` and `golarion_model` therefore have a static-library dependency cycle, handled by CMake's repeated archive linking. Public target names and the C boundary are unchanged; see `model/equipment.md`.
- Rule categories are a closed system and must use enum classes. JSON may use stable English names, but parsers reject names outside the enum vocabulary. IDs and descriptive text remain strings. The current change aligns spell metadata and feat types/slot filters/Views; it does not silently migrate unrelated existing subsystems.
- `core/` is the backend module container; `core/CMakeLists.txt` adds `sheet` and `play`. The sheet engine, catalogs, persistence, C bindings, and tests live in `core/sheet/`; `core/play/` owns the independent C++20 session model, function registry, background TCP hosting, and the Session-based console host.
- `golarion::play::Session` is a container/facade, requires a host user ID, and declares ResourceManager before ProtocolManager and RoleManager. Both managers receive the registry by reference. Registration precedes later providers; role lookup is deferred until dispatch. The registry outlives providers. Session stops hosting before member teardown, keeping RoleManager and registered providers alive until the worker joins. Client-side ProtocolManager remains unimplemented.
- ProtocolManager directly owns logical connection maps and the ID counter; no separate ConnectionManager is introduced. Session delegates registration, binding/replacement, context construction, and close. `getUserId` remains only on ProtocolManager, and no connection features are published through ResourceManager. ProtocolManager also owns private `detail::UserTokens` and identity archive operations; Session delegates issuance/save/load and RoleManager registration. There is no SessionId. RoleManager remains the sole runtime owner of roles; binding does not create users or assign roles. See `session-protocol.md` and `session-tokens.md`.
- SessionCode is an independent value type owned as a const member by ProtocolManager, generated before feature registration and unchanged by start/stop. Session delegates its display getter; verification stays on ProtocolManager and is not a registry feature. The user deferred host-wide uniqueness and persistence, so generation currently yields a candidate only; see `session-protocol.md`.
- The application target is native desktop software in C++. A minimal API with C linkage already exposes the sheet through FFI. Whether the future desktop frontend uses that boundary or a typed C++ application interface remains open; see `game-management.md` for the game-management design proposal.
- C++ types, STL containers, ownership, and exceptions do not cross the C API boundary.
- Complex frontend snapshots may later be exchanged as JSON. ProtocolManager already uses `nlohmann_json` 3.12 for backend command payloads/results; frontend contracts remain undecided.
- GUI snapshots use `View`/`toView`; future persistence structures will use `SaveData`/`toSaveData` to keep calculated presentation state separate from serialized source state.
- Character-sheet components register enhanceable resources by name; they neither create nor retain their `ModifierSet`.
- `golarion::play::ResourceManager` is shared only by reference among one Session's subsystems. It is separate from the sheet-specific `golarion::ResourceManager`; no sheet behavior is moved into it. Its implementation and tests live in `core/play/`.
- RoleManager implements synchronized registration, lookup, minimum-role checks, authorized changes, and validated snapshots. Its seven features are `roles.registerUser`, `roles.getRole`, `roles.hasAtLeastRole`, `roles.setRole`, `roles.toSaveData`, `roles.restoreSaveData`, and `roles.registerUserWithCommit`; see `session-roles.md`. The last stages a Player and commits only after the supplied snapshot callback succeeds, allowing ProtocolManager to persist roles/tokens together during admission. Mutations enforce target-specific restrictions; restore preserves the immutable Host identity. Commit callbacks must not reenter managers.
- ProtocolManager exposes only `protocol.add_command`. Its constructor first registers join/resume with minimum Any in the same command registry; ordinary duplicate checks/normalization protect both names. Common dispatch serves local, anonymous pending, and authenticated network calls, validates live records/optional identities/current roles, and preserves callback state/results. Every permission check uses RoleManager through ResourceManager; Any is only a nonassignable threshold below Spectator. A recursive execution mutex serializes registration, execution, admission, and binding changes; callbacks hold no connection/role lock. Admission locks execution, identity, connections, then roles; load adds lifecycle first. Stop joins without execution locked; lifecycle/load calls from callbacks are rejected before locking. See `protocol-manager.md` and `session-commands.md`.
- The private codec retains generic JSON v2 encode/decode independent of roles/context. Hosting uses it for framing and existing `admission.cpp` handles every request through dispatch, wraps all successes in `request.accepted` / `payload.result`, and builds shared rejections. Closed `ProtocolErrorCode`/`ProtocolError` supply typed outcomes. The prefix is four bytes and cap 64 KiB; invalid output becomes `COMMAND_FAILED` without retry. Client support, concrete role/sheet commands, user-list events, and display names remain deferred; see `session-protocol.md`.
- Automatic condition generation from independent character-sheet state is deliberately limited to `Barcollante`, `Privo di Sensi`, `Inabile`, `Morente`, `Stabilizzato`, and `Morto`. A condition definition may still generate another condition when the latter is a mandatory rules consequence, such as `Privo di Sensi` producing `Indifeso` or `Immobilizzato` producing `Impreparato`; the derived entry exists only while its source condition requires it. Every other character condition requires an explicit external source entry. `Impreparato` is not generated from encounter state because encounter-state integration is not implemented; a future play module may supply it, while `Rotto` is excluded because it is a condition of individual objects rather than of the character.

## Session ResourceManager

- `registerFeature<Signature>(name, callback)` owns a nonempty `std::function<Signature>` under a unique name. Callbacks must be copy constructible, as required by `std::function`.
- `invoke<Signature>(name, arguments...)` checks the exact registered signature, including return type and reference qualifiers, before forwarding arguments and returning the callback's result. Void and reference returns and move-only arguments are supported. Mutable callback state survives successive calls.
- `unregisterFeature(name)` removes the registration; the name can subsequently be reused with another signature. Calls already in progress retain the original callable until they return, including when a callback removes or replaces its own registration. Nested invocations are supported.
- Names are case sensitive, with outer ASCII whitespace trimmed consistently in all operations. Empty/whitespace-only names, empty callbacks, duplicate registrations, missing features, and signature mismatches throw `std::invalid_argument`. Callback exceptions propagate unchanged.
- Providers must outlive callbacks; finish local calls and stop the worker before teardown. ResourceManager/Session cannot be copied/moved. Finish registry feature registration before hosting; concurrent lookup of unchanged features is supported, while registry mutation remains serialized. RoleManager synchronizes its data and ProtocolManager serializes local/remote callbacks and command registration. Independent provider access retains its own threading contract. The registry does not interpret roles, TCP, or JSON.

```cpp
resources.registerFeature<int(int)>("example.double", [](int value) { return value * 2; });
const int result = resources.invoke<int(int)>("example.double", 3);
resources.unregisterFeature("example.double");
```
