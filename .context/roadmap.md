# Roadmap

## Pending Work

The user deferred all concrete racial catalog connections (including languages, bonus feats and immunities) to the complete dataset effort. The catalog items below are deferred work, not authorization to start them next.

- Session now owns a typed function registry and RoleManager, initialized with an explicit host user ID. Role lookup, minimum-role checks, and protected role changes are implemented and tested; see `session-roles.md`. Add ProtocolManager command registration and identity management in separate changes, passing the registry by reference to new subsystems. Finalize the detailed JSON-over-TCP message schemas in `session-protocol.md` before network integration. Codes, per-session permanent identity tokens, and replacement of old connections are confirmed but not implemented. The binary TCP prototype remains separate; add the contract and persistence incrementally.
- Typed structural/casting effect bridges and feat prerequisite alternatives are implemented; see `model/effect-endpoints.md`. Migrate concrete core-race reminders/providers where supported; all seven standard profiles are already present. Add the separate catalog View needed to choose a race and its alternate features. Runtime mechanics must never be inferred from Italian names or descriptions.
- The planned structured `SpecialDefenses` categories are complete for the informational sheet model. Concrete sources such as Resistenza Potenziata and Veste della Regina Fatata must register Reminder entries for their contextual exceptions. Decide the exceptional conversion of energy resistance above a threshold into immunity when the first canonical source requires it; the current RE model deliberately performs no such implicit conversion.
- Channel resistance is not a new `SpecialDefenses` category: canonical Resistenza ad Incanalare is a conditional bonus to Will saves and should use the existing conditional Modifier pipeline. Fortification and event-resolution capabilities such as Evasion are informational/reminder concerns unless a future incoming-attack or saving-throw resolver gives them structured context.
- Add a native typed singleton-resource protocol to `ResourceManager`. `size.base`, `carryingCapacity.bodyType`, and `carryingCapacity.size` currently use collection resources constrained by their owning components to zero or one entry; migrate them once singleton registration, replacement, removal, type checking, and View exposure have shared semantics.
- Carrying-only Strength modifiers and rational multipliers already cover independent load changes. Do not treat carrying-specific effective size as a blocker without a concrete source that cannot use these endpoints. Body-changing transformations may eventually need a replacement stage above the race-owned body base.
- Conditional hand-usage permissions are now available through `attackRoutine.handUsagePermissions`, separate from WeaponWeight and optionally scoped to a routine/slot. The `handUsagePermission` declarative effect is implemented; add concrete providers for exceptional weapon uses; associated penalties/damage exceptions remain separate contributions. This does not yet implement every crossbow, lance, proficiency or double-weapon rule. Routine hand usage currently does not synthesize extra physical `usageChannels`; coordinate that with the future anatomy/held-object model before relying on it to suppress natural attacks from every occupied limb.
- Review the modifier fields and C++ representation together.
- Design richer C API operations only when the corresponding model behavior exists.
- Add an explicit resurrection protocol before any effect can remove the persistent hit-point-owned Morto entry or restore a dead character; ordinary healing intentionally does neither.
- Selective Dexterity retention is implemented with explicit suppression causes and the `armorClass.dexterityRetentions` endpoint/effect; FlatFooted and InvisibleAttacker can be retained, while Pinned, Feint and Other remain effective. Concrete Schivare Prodigioso providers remain catalog work. Attacks-of-opportunity allowances/exceptions need turn/action resolution; the existing ActionManager does not track turns.
- Add turn-state tracking before enforcing the remaining one-action-per-turn rules of `Barcollante`, `Inabile`, and `Nauseato`; the current deterministic prohibitions are already represented through `ActionInhibition`. Add semantic metadata for purely mental actions before restricting `Paralizzato`, and for attacks of opportunity and two-handed routine use before completing `Impreparato` and `In Lotta`.
- When spellcasting is modeled, replace `Intralciato`'s Concentration reminder with an actual check requirement using CD 15 + spell level; a failure loses the spell.
- Design a dedicated `TimeManager` as the sole owner of game-time advancement. Components should register subscribers or scheduled reversible actions with it; temporary-hit-point pools may retain duration metadata for optimal damage allocation but must not advance or expire themselves. Persistence and safe unsubscription semantics must be decided when this manager is introduced.
- When `TimeManager` is implemented, revisit `TemporaryHitPoints`: replace its static declared-duration ordering with actual remaining time supplied by the manager, consume the pool whose timer expires first, keep untimed pools last, remove expired grants through the collection protocol, and move timer persistence out of the temporary-hit-point SaveData into the central time system.
- Complete movement's remaining rule pipeline when armor is modeled. Carried-load reduction now uses the official adjusted-movement table and the same idempotent adjustment type is ready for armor. `movement.boundedBonuses` now caps each bonus against the ordinary-speed baseline while preserving modifier stacking and movement adjustments; concrete Haste providers remain catalog/cast-resolution work.
- Concrete feat providers can use the implemented `runAdjustment` effect: `Correre` should register a +1 run multiplier adjustment and `Correre (Mitico)` an additional +2 in a distinct stacking group, producing ×5/×4 and ×7/×6 with light-or-no/heavy armor or load respectively. Keeping the Dexterity bonus to armor class while running is a separate action-context rule and remains pending.

## After the Character Sheet

- Decide whether conditional ability substitutions need explicit model support. A possible implementation is a signed, non-stacking delta modifier such as `-@wisMod + @chaMod`, shared by skills and saving throws. This is optional: the application may instead leave situational substitutions for the player to remember and apply at the table.
- Design the complete C API only after the C++ character-sheet model has stabilized.
- Select and build the native desktop C++ frontend. Resolve its application API boundary as part of the new game-management design; the toolkit and implementation schedule remain open.
