# GolarionHelper Context

## Goal

Build a local-first Pathfinder 1e character-sheet engine in C++, kept independent from its future portable frontend.

## Current State

- Development is taking place on the orphan branch `cpp-rebuild`.
- The previous Java model rebuild is preserved on `model-rebuild` at commit `e99d776`.
- The project currently contains only a minimal C++20 backend.
- `CharacterSheet` owns and initializes one `ResourceManager` before registering its model components. It also owns `Skills` and exposes only rank changes plus creation/removal of user-defined specializations, without model getters or a user-facing class-skill setter. Removing a user-defined specialization unregisters its resource and fails while a structural modifier or skill option still targets it. Canonical specializations cannot be removed.
- `CharacterSheet` owns `Movement`, which starts with a provisional structural racial land-speed grant of 6 movement units (9 m). Race modeling will eventually replace this placeholder and rebuild the appropriate grant at startup. The sheet exposes no user-facing movement mutation.
- Movement uses integer units of 1.5 m and supports land, climb, swim, burrow, and fly modes. Fly grants carry maneuverability (clumsy, poor, average, good, or perfect) and its Pathfinder Fly-check modifier.
- Every movement grant is an independent, atomic profile identified by a stable ID and source. Multiple grants of the same type remain separate alternatives rather than merging speed and properties field by field.
- Each grant registers an enhanceable resource beneath `speed.all`, `speed.<type>`, and `speed.<type>.<grantId>`. Additive speed bonuses therefore reuse normal modifier stacking at global, movement-type, or exact-grant scope.
- `MovementAdjustment` handles non-additive transformations selected globally, by movement type, or by exact grant: percentage speed multipliers, absolute speed limits, maneuverability shifts, and movement blocks. Conditional adjustments are resolved for display but do not alter the permanent result.
- A grant cannot be removed while an exact-grant adjustment or a direct modifier still targets it. Dependents must be removed first, preventing one group from silently mutating another. `MovementView` exposes every independently resolved profile, its modifier snapshot, applicable adjustments, effective speed, maneuverability, and usability.
- The six abilities start at 10, validate positive base values, and register an enhanceable resource plus total/modifier targets using `str`/`strMod`, `dex`/`dexMod`, `con`/`conMod`, `int`/`intMod`, `wis`/`wisMod`, and `cha`/`chaMod`.
- `BaseAttackBonus` owns the accumulated `baseAttackBonus` resource and exposes its total as the `bab` expression target. It starts at 0, rejects a negative resolved total, has no user setter or persistence data, and will receive structural contributions from character classes and Hit Dice. `CharacterSheetView` includes its total and complete contribution breakdown.
- The first attack-model slice separates delivery mode from combinable traits: `AttackMode` distinguishes melee and ranged attack rolls, while `AttackTag` identifies weapon, thrown, projectile, natural, unarmed, primary, and secondary attacks without conflating those dimensions.
- `AttackGrant` is an immutable structural definition with stable identity, provenance, display name, mode, tags, a `DamageAbilityRule`, and base critical threat/multiplier. Melee and ranged modes structurally map to Strength and Dexterity for their default attack ability.
- `Attacks` registers the typed `attack.grants` collection with `ResourceManager` and owns every added grant. For each grant it creates `attack.grant.<id>`, `damage.grant.<id>`, and `criticalConfirmation.grant.<id>` enhanceable resources beneath their applicable mode and tag categories. Removing a grant unregisters all three atomically and is rejected while an exact resource still has a direct modifier.
- `CombatManeuvers` models Bull Rush, Dirty Trick, Disarm, Drag, Grapple, Overrun, Reposition, Steal, Sunder, and Trip independently from concrete attacks. Every maneuver has BMC and CMD resources beneath `combatManeuver.bonus.all` and `combatManeuver.defense.all`; the common BMC resource inherits `attack.all`, because combat maneuver checks are attack rolls.
- BMC is calculated from BAB, Strength by default, the shared accumulated special-size modifier, and applicable modifiers. Components register `CombatManeuverAbilityReplacement` entries globally or against one maneuver resource; each View contains the fully calculated default and applicable replacement options without persisting a selection. CMD is calculated from 10, BAB, Strength, Dexterity, the same size modifier, and its own global/per-maneuver modifiers.
- `CharacterSheet` owns `Attacks` before `CombatManeuvers`, ensuring the attack resource hierarchy exists before BMC inherits from it. `CharacterSheetView` includes calculated attacks and all ten BMC/CMD results. Weapon-specific maneuver options, flat-footed CMD, selective propagation of eligible AC modifiers, BAB replacements, and the future `Size` component remain later combat steps.
- `DamageDice` is a validated immutable dice expression with positive dice count and die size. It normally exposes the canonical `XdY` representation; a `d1` result from the weapon-size progression is displayed as fixed damage. `DamageType` distinguishes physical, elemental energy, force, positive/negative energy, and untyped hit-point damage; precision, bleed, non-lethal application, materials, alignment, and magical attacks remain separate properties rather than damage types.
- `DamageTypeMode` distinguishes components whose listed types all apply from components that let the user choose one type. Every damage enum value has an Italian `displayName()` for GUI use.
- `DamageComponent` is an immutable identified damage source containing dice, one or more damage types, their all/choice semantics, critical behavior, and optional precision, bleed, or non-lethal traits. It rejects empty or duplicate types, meaningless one-type choices, untyped damage mixed with typed damage, duplicate traits, and precision damage marked as multiplied on a critical hit.
- `AttackGrant` owns zero or more damage components and requires their IDs to be unique within the attack. Zero components remain valid for attacks that deliver an effect without direct hit-point damage.
- Every damage component has a structural `Base` or `Additional` role. `Attacks` registers the typed `damage.diceAdjustments` collection so independent components can alter matching damage dice through the existing damage resource hierarchy, optionally restricting an adjustment to one component ID. This keeps future size, spell, equipment, and class-feature components independent from `Attacks`.
- Damage-dice adjustments can move by signed steps through the Pathfinder weapon-damage progression, multiply the number of dice, or establish a replacement die expression. Permanent adjustments produce each component's effective dice; conditional adjustments are calculated separately per condition. The GUI view exposes the base dice, effective dice, conditional results, and complete adjustment provenance.
- Attack distance uses 1.5-metre grid units, matching movement. Melee grants define an optional inclusive minimum/maximum reach interval, including zero reach; ranged grants may define their range increment, maximum number of increments, and penalty for every increment after the first. Thrown attacks normally use five increments and projectile attacks ten, but these remain explicit grant data so exceptional attacks are representable.
- Each distance property has an independent enhanceable hierarchy with global, melee/ranged, attack-tag, and exact-grant resources. Normal modifiers handle additive changes, while entries in the typed `attack.distanceAdjustments` collection apply additive-combination multipliers, lower bounds, or upper bounds. Permanent and per-condition results plus complete provenance are exposed in `AttackView`, allowing feats, spells, equipment, and future size components to affect reach or range without mutating an attack grant.
- An `AttackGrant` may carry structural `Requirement` values, while components add or remove external `AttackRequirement` entries through the typed `attack.requirements` collection. External requirements target the normal attack resource hierarchy and may therefore affect all attacks, a mode, a tag, or one exact grant without removing it from the sheet.
- `AttackView` always retains the attack and exposes its permanent `usable` state, active failure reasons, every evaluated requirement with provenance, and separate usability results for named situational conditions. Conditional requirements do not disable the ordinary attack; they describe whether it is usable when their condition applies. Exact external requirements prevent the owning attack grant from being removed until the dependency is removed.
- Every `AttackGrant` declares its structural target defense using the existing `ArmorClassType` values: normal, touch, or flat-footed AC. Components register `AttackDefenseReplacement` entries through the typed `attack.defenseReplacements` collection to add alternative defenses for an attack hierarchy target, optionally limited to a named condition such as being within a firearm's first range increment.
- The backend does not select among defense alternatives because target state and distance are encounter inputs. `AttackView` exposes the base defense first and every applicable replacement with identity, provenance, and condition so the GUI can present the valid comparison. Exact defense replacements prevent removal of their attack grant until the dependency is removed.
- `Attacks` also registers the typed `damage.componentGrants` collection. A `DamageComponentGrant` contributes one external component to every attack whose exact damage resource inherits from its target, allowing effects to address `damage.all`, a mode, a tag, or `damage.grant.<id>` without mutating the immutable `AttackGrant`. Grant IDs are globally unique and removing an attack is rejected while an external component directly targets it. Calculated attack views will merge intrinsic and applicable external components dynamically.
- Critical-confirmation modifiers use a parallel hierarchy rooted at `criticalConfirmation.all`, with mode, tag, and exact-grant resources. An exact confirmation resource also inherits its exact attack resource, so confirmation automatically receives every normal attack modifier plus confirmation-only modifiers. Exact confirmation resources participate in the same atomic attack registration/removal rollback.
- `Attacks` registers the typed `attack.criticalAdjustments` collection for non-additive critical-profile changes. A `CriticalAdjustment` targets an attack resource and describes a threat-range multiplier, direct threat minimum, critical-multiplier increase, or direct multiplier value using an expression; multiplier increases may carry a maximum, and every adjustment may be conditional. Exact adjustments prevent their attack from being removed until the adjustment is removed.
- `AttacksView` exposes every calculated attack. A normal attack combines BAB, the mode's default ability (Strength for melee, Dexterity for ranged), the inherited attack modifier set, and the automatic -5 secondary-natural-attack penalty. Non-natural attacks derive their complete -5 iterative sequence from BAB; natural attacks remain single entries.
- Each `AttackView` includes its confirmation total and modifiers, permanent and per-condition resolved critical profiles, every resolved critical adjustment, the current Strength damage ability and its contribution under the attack's `DamageAbilityRule`, permanent normal/critical flat damage bonuses, and all intrinsic plus applicable externally granted damage components. Component snapshots expose dice numerically and as `XdY`, provenance, types/traits, normal inclusion, and the number of critical occurrences.
- Threat-range multipliers use only the greatest applicable multiplier, matching the non-stacking rule for effects such as Keen and Improved Critical; direct threat minima use the most favorable threshold. Critical multiplier sets use the greatest value, increases accumulate, and any declared caps constrain the final result. Conditional adjustments are combined with the permanent profile separately for each condition.
- Components can register `AttackAbilityReplacement` and `DamageAbilityReplacement` entries through separate typed collections. Each replacement has stable identity, provenance, an attack/damage hierarchy target, and an ability; it applies to the target and every descendant. Exact replacements prevent removal of their attack until the dependency is removed.
- `AttackView` never selects an ability replacement. It exposes a calculated base attack-ability option plus every applicable replacement, each with its own iterative bonuses and confirmation total; damage follows the same pattern, preserving the attack's `DamageAbilityRule` while recalculating the ability contribution and normal/critical flat bonuses.
- `SkillType` defines the standard Pathfinder skills and their fixed metadata: display label, resource name, default ability, trained-only status, specialization requirement, and armor-check-penalty applicability.
- `Skill` models one concrete skill entry, including specialized Craft/Perform/Profession entries, and registers only an enhanceable resource. Skills are deliberately not expression targets; each calculated option combines its ability modifier, ranks, the trained class-skill bonus, and the skill's `ResourceManager` modifiers.
- `Skills` owns all non-specialized standard skills and Craft/Perform/Profession entries. It creates and registers the canonical specializations at initialization and allows additional user-defined specializations. Canonical specializations remain present in the model; eventual visibility filtering belongs to the GUI.
- Components may register `SkillAbilityReplacement` entries through `skill.abilityReplacements`, identifying an ID, source, target skill resource, and replacement ability. A replacement applies to its exact target and every descendant in the skill resource hierarchy, so category replacements automatically cover existing and future specializations. Duplicate IDs, missing resources, and non-skill targets are rejected.
- Components grant class-skill status through `SkillClassSkillGrant` entries registered in `skill.classSkillGrants`. Each grant records a stable ID, source, and target skill resource, and applies to that resource and all descendants; a category grant therefore covers existing and future specializations. Duplicate IDs, missing resources, and non-skill targets are rejected.
- `SkillView` exposes identity, display name, derived class-skill status and bonus, every applicable class-skill grant with provenance, ranks, usability, resolved modifiers, whether the entry is custom, and a fully calculated default ability option plus every applicable replacement. The backend never selects an ability option; the GUI chooses which valid result to display. `SkillsView` provides every concrete skill in deterministic type/specialization order and is included in `CharacterSheetView`.
- `SkillSaveData` stores only user-owned source state for one concrete skill: identity, custom specialization metadata, and ranks. Class-skill grants, ability associations, and component-owned replacements are reconstructed rather than persisted. `SkillsSaveData` stores the complete deterministic skill collection; loading recreates custom resources before modifier groups and validates built-in completeness, identity uniqueness, and canonical/custom classification.
- `SavingThrow` models Fortitude, Reflex, or Will with its structural default ability: Constitution, Dexterity, or Wisdom. `SavingThrows` owns all three and registers `savingThrow.all` plus the concrete enhanceable resources so global and per-save modifiers compose through inheritance. Each save also owns an accumulated `savingThrow.<type>.base` resource; class and other structural contributions build its base bonus automatically.
- Components may register independent `SavingThrowAbilityReplacement` entries through `savingThrow.abilityReplacements`, identifying their stable ID, source, affected save, and replacement ability. Duplicate IDs are rejected. The backend never selects or persists an alternative: each `SavingThrowView` contains the fully calculated default option and every registered replacement, while the GUI chooses which valid result to display.
- `SavingThrowView` also exposes the resolved base value, its complete contribution set, and common permanent/conditional modifier information. `SavingThrowSaveData` and `SavingThrowsSaveData` no longer exist because base values, default abilities, and replacements are reconstructed by components. `CharacterSheet` exposes no saving-throw mutation.
- `Initiative` registers the `initiative` enhanceable resource and uses Dexterity as its structural option. Components may register independent `InitiativeAbilityReplacement` entries through `initiative.abilityReplacements`; `InitiativeView` exposes the fully calculated Dexterity option and every replacement, while the backend never selects or persists one. `InitiativeSaveData` no longer exists because initiative has no user-owned source state.
- `ArmorClass` calculates normal, touch, and flat-footed AC from a base of 10, Dexterity, and inherited modifier resources. Positive ability modifiers are capped by the optional maximum Dexterity bonus for normal and touch AC; flat-footed AC removes a positive modifier but preserves a negative one.
- Armor-class modifier applicability is represented by a resource graph: `armorClass.all` feeds every variant, `armorClass.reflexive` feeds normal and touch AC, `armorClass.solid` feeds normal and flat-footed AC, and each concrete variant has its own resource for exceptional effects. Calculated armor-class values are not expression targets because there is currently no concrete consumer for them.
- Maximum Dexterity is modeled as a typed collection of independent limits rather than one mutable value. Armor, shield, load, and other sources add `MaximumDexterityLimit` entries through `armorClass.maxDexLimits`; no entries means no limit, and the effective maximum is the lowest active resolved limit.
- Each maximum-Dexterity category inherits from `armorClass.maxDex.all`, while every dynamic `armorClass.maxDex.limit.<id>` resource inherits from its category. Normal modifiers can therefore adjust every limit, only armor/shield/load/other limits, or one exact source. Removing a limit is rejected while its exact resource still contains modifiers. Limit results are clamped to zero.
- Components may register independent `ArmorClassAbilityReplacement` entries through `armorClass.abilityReplacements`. The backend never selects or persists one: `ArmorClassView` always exposes the complete Dexterity-based option plus one fully calculated option per registered replacement, and the GUI decides which valid option to display. Duplicate replacement IDs are rejected and removing a missing entry fails.
- `ArmorClassView` also exposes the effective maximum Dexterity bonus and every source limit with its base/effective values and modifiers. Each ability option contains its raw ability contribution and separate resolved entries for normal, touch, and flat-footed AC. There is no `ArmorClassSaveData`: substitutions and limits are reconstructed by their owning class, talent, equipment, load, or effect component.
- `CharacterSheet` owns `ArmorClass` and includes it in GUI snapshots, but deliberately exposes no operation for users to change its defensive ability, register arbitrary substitutions, or directly set maximum-Dexterity limits. Uncanny-dodge behavior remains a subsequent armor-class step.
- `HitPoints` stores base maximum, lethal damage taken, temporary hit points, and non-lethal damage. Its effective maximum adds the accumulated `hp.max` contributions and never drops below zero; current hit points are derived as `max - damageTaken`, so maximum changes automatically adjust current hit points while preserving wounds. `hp.max` is an accumulated resource, while none of the hit-point values are expression targets.
- `CharacterSheet` registers `level` as an expression target that currently always resolves to 1, then installs the structural `hitPoints.constitution` contribution on `hp.max` with expression `@conMod * @level`. This contribution is rebuilt at startup and is not persisted. Character level is a temporary approximation for Hit Dice; racial Hit Dice and the minimum of 1 hit point per Hit Die remain future concerns.
- `HitPoints::damage` consumes temporary hit points first, then applies lethal damage to current hit points or accumulates non-lethal damage up to the effective maximum and converts overflow to lethal damage. `HitPoints::heal` restores current hit points up to the effective maximum and removes the same amount of non-lethal damage without restoring temporary hit points.
- Hit-point damage application uses `DamageLethality` (`Lethal` or `NonLethal`), keeping that concern distinct from the attack model's `DamageType` categories.
- Temporary hit points are stored as independent source pools rather than one integer. Each pool has a user-provided normalized ID, remaining points, and an optional `GameDuration`; different IDs stack, while reapplying the same ID keeps the stronger remaining amount and, on a tie, the longer duration. Damage consumes pools by shortest remaining duration first, indefinite pools last, and expiration removes remaining points without transferring damage.
- `GameDuration` stores non-negative game time in rounds and provides checked factories for rounds, minutes, and hours. `CharacterSheet::advanceTime` currently advances temporary-hit-point durations and can later be extended to other timed effects.
- `HitPointsView` exposes all four sheet values, individual temporary-hit-point pools, and the resolved maximum contribution set. `HitPointsSaveData` persists internal base maximum, damage taken, temporary pools, and non-lethal damage, while calculated maximum/current totals are derived and structural contributions are reconstructed by their owning components. `CharacterSheet` exposes only healing, typed damage, and time advancement as user-facing hit-point interactions. Temporary pools are added and removed internally through the `hp.temporary` collection by their owning components.
- The first modifier-domain slice is implemented: modifier enums, stacking metadata, immutable modifier data, UUID generation, normalization, and constructor invariants.
- `BonusType::Generic` represents bonuses without a more specific Pathfinder type. Generic bonuses always stack.
- `ResourceManager` owns the `ModifierSet` of every registered enhanceable resource and keeps live integer targets in a separate normalized registry. It routes modifier additions/removals, calculates totals by resource name, and detects circular target resolution.
- `ResourceManager` supports typed collection resources as its third resource category. A component registers a normalized resource name, its item type, and add/remove callbacks; callers add strongly typed values through the global manager, while an incompatible item type is rejected before dispatch. Collection names remain available through the manager's diagnostic `ResourceManagerView`, which is not exposed by `CharacterSheetView`.
- `Movement` registers `movement.grants` for `MovementGrant` values and `movement.adjustments` for `MovementAdjustment` values. `HitPoints` registers `hp.temporary` for `TemporaryHitPointGrant` values; the grant amount is an integer expression resolved through the manager when added. The component remains the owner of its state and rules, while `ResourceManager` only validates and routes collection operations.
- `CharacterSheet` installs only its provisional racial movement grant directly through the registered collection resource. `Movement` has no save root: grants and adjustments are reconstructed by their owning race, class, item, condition, or effect component. Hit-point persistence still stores mutable remaining temporary pools. The collection registry is always reconstructed at startup.
- `ResourceManager` also supports accumulated resources backed by `ContributionSet`. Each `Contribution` has an explicit normalized ID and an integer expression; all contributions stack, may resolve to signed values, and can be added or removed independently without modifier types, conditions, or stacking rules. `HitPoints` uses this mechanism for its effective maximum.
- Enhanceable resources may inherit from already registered parent resources. Totals and views combine direct and inherited modifiers before applying stacking rules, deduplicate shared ancestors in multiple-inheritance graphs, and automatically expose category modifiers to resources registered later.
- Skill modifiers use a resource hierarchy rooted at `skill.all`. `skill.craft`, `skill.perform`, `skill.profession`, `skill.knowledge`, and `skill.armorCheckPenalty` inherit from that root. Craft/Perform/Profession specializations inherit from their respective category, Knowledge skills inherit from `skill.knowledge`, armor-check-penalty skills inherit from `skill.armorCheckPenalty`, and every other concrete skill inherits directly from `skill.all`. Consequently global and category modifiers automatically reach existing and future descendants without each skill listing all applicable categories.
- Integer expressions support literals, registered targets prefixed by `@`, parentheses, unary signs, whitespace, the four basic arithmetic operators with integer division, comparisons, and the logical operators `!`, `&&`, and `||`; logical results are represented as 0 or 1.
- `Requirement` is a reusable expression plus a GUI-facing failure reason. A `Modifier` may own multiple requirements, all of which must resolve to nonzero before it participates in permanent or conditional stacking. Inapplicable modifiers remain in `ModifierView` with their resolved value, active state, and individual requirement results.
- `ModifierSet` calculates permanent totals through `ResourceManager`, applies Pathfinder stacking rules, caps inherent bonuses at +5, subtracts all penalties, excludes conditional modifiers, and rejects negative resolved magnitudes.
- `ModifierView` exposes every modifier field plus its resolved value. `ModifierSetView` contains the permanent total, effective conditional deltas grouped by condition, and all resolved modifier snapshots; each expression is evaluated once per set snapshot.
- `AbilityView` contains the ability type, base value, total value, derived modifier, and its complete `ModifierSetView`; `AbilityScore::toView` resolves the modifier set once per snapshot.
- `AbilitySaveData` contains only the ability type and base value; calculated values and modifier snapshots are rebuilt rather than persisted.
- `ContributionView` contains the ID, expression, and resolved value; `ContributionSetView` adds the accumulated total. Group and manager views expose targeted contributions and deterministically ordered group states.
- There is no persistence data for modifiers, requirements, contributions, movement grants, movement adjustments, or registered resource sets. These are structural objects reconstructed by their owning model components; only their resolved GUI views remain.
- `CharacterSheetSaveData` is the versioned persistence root and contains only ability, hit-point, and skill source data; armor class, initiative, saving throws, `ResourceManager`, modifiers, contributions, and movement have no direct save data because their state is rebuilt by model components. The current format version is 14; versions 8, 10, 11, 12, and 13 remain loadable. Obsolete modifier, contribution, and movement group fields in older JSON are ignored. The unreleased version 9 movement-root experiment is intentionally rejected because it could not distinguish structural from user-owned grants.
- The separate `golarion_persistence` library converts `CharacterSheetSaveData` to and from readable JSON through `nlohmann-json`; persistence enum names are stable English identifiers and do not reuse GUI labels.
- `CharacterSheet::save(path)` delegates JSON file writing to the persistence module and reports file opening or writing failures with exceptions.
- `CharacterSheet::load(path)` validates format version and the complete set of six abilities, restores user-owned source values, and lets model components reconstruct all structural modifiers, contributions, grants, and adjustments. Armor-class substitutions and limits are not loaded from JSON.
- Manual modifier, contribution, and movement groups, their managers, GUI views, save data, JSON sections, sheet APIs, and tests have been removed. The autonomous model currently has no extension point for house rules; concrete components interact directly with `ResourceManager`.
- `ResourceManagerView` remains a diagnostic snapshot used by focused manager and resource-hierarchy tests. It exposes registered targets, collections, and enhanceable resources with their resolved modifiers, but is deliberately not part of the GUI-facing sheet snapshot.
- `CharacterSheetView` aggregates abilities, hit points, initiative, armor class, saving throws, skills, and resolved movement for the GUI.
- A minimal C-compatible API creates and destroys opaque character-sheet handles.
- Further C API design is deferred until the C++ model is complete; current model additions are not exposed through FFI.
- CMake builds the model, shared interoperability library, and smoke test.
- Frontend work is explicitly deferred.
- Backend headers, implementations, and tests mirror the logical areas `character`, `resource`, `view`, `data`, `persistence`, `util`, and `ffi`; modifiers and contributions both live under `resource`, while all GUI snapshot structs are collected under `include/golarion/view` and use the `View` suffix.

## Important Decisions

- The domain model is implemented in modern C++.
- A thin API with C linkage will be the only boundary exposed to a future frontend through FFI.
- C++ types, STL containers, ownership, and exceptions do not cross that boundary.
- Complex frontend snapshots may later be exchanged as JSON, but no serialization dependency is introduced yet.
- GUI snapshots use `View`/`toView`; future persistence structures will use `SaveData`/`toSaveData` to keep calculated presentation state separate from serialized source state.
- Character-sheet components register enhanceable resources by name; they neither create nor retain their `ModifierSet`.

## Setup

```sh
cmake -S . -B build
cmake --build build
ctest --test-dir build --output-on-failure
```

The JSON module requires the `nlohmann-json` package (`yay -S nlohmann-json` on Arch Linux).

## Pending Work

- Review the modifier fields and C++ representation together.
- Design richer C API operations only when the corresponding model behavior exists.
- When the condition system is implemented, connect it to `HitPoints`: 0 current hit points should apply disabled, negative hit points should apply dying and unconscious, reaching the negative Constitution threshold should apply dead, non-lethal damage equal to current hit points should apply staggered, and non-lethal damage above current hit points should apply unconscious. Keep this deferred until conditions have a dedicated model rather than embedding provisional condition logic in `HitPoints`.
- Evolve `CharacterSheet::advanceTime` into the central game-time propagation mechanism for all duration-based effects, including conditions, spells, class features, item effects, and other temporary resources. It currently advances only temporary-hit-point pools; introduce a shared time/effect protocol when the first additional timed subsystem is modeled.
- Complete movement's rule pipeline when armor, carried load, and conditions are modeled. `MovementGrant` already records whether armor and load apply, but those reductions are not calculated yet. Effects with a bounded increase such as `Haste` also need an explicit final-speed stage so the +9 m enhancement bonus can be capped at twice the pre-effect normal speed without bypassing stacking rules.

## After the Character Sheet

- Decide whether conditional ability substitutions need explicit model support. A possible implementation is a signed, non-stacking delta modifier such as `-@wisMod + @chaMod`, shared by skills and saving throws. This is optional: the application may instead leave situational substitutions for the player to remember and apply at the table.
- Design the complete C API only after the C++ character-sheet model has stabilized.
- Select and build the portable frontend after the backend and C API are complete.
